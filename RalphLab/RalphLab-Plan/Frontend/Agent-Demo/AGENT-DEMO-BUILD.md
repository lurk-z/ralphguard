# ลำดับสร้างเดโม FE และจุดต่อ API

อ่าน [[AGENT-DEMO-SPEC]] ก่อน เริ่มจากพิสูจน์การส่งงานหนึ่งครั้งให้ครบตั้งแต่ผู้ใช้พิมพ์จนผู้รับตอบ แล้วจึงเพิ่มฉากและกิ่งสูตร วิธีนี้ช่วยแยกได้ว่าอาการ “เดินถึงแล้วแต่ไม่ตอบ” เกิดจากข้อมูลส่งไม่ถึง หรือ UI ยังรอภาพเคลื่อนไหว

## ฐานเดิมที่ให้ตรวจใน checkout ที่ใช้แข่ง

เริ่มที่ [[JAY-FRONTEND-BASELINE]] ตารางด้านล่างรวมพาธจากเดโมที่เตรียมใน sandbox ด้วย เมื่อเริ่มบน `jay-frontend` ให้ตรวจสิทธิ์โค้ดและโมเดลแยกกัน จุดตรวจแรกให้เปิด Lab เลือก Agent จากฉากหรือรายชื่อ พิมพ์ ส่ง และเห็นคำตอบในแชตนั้น จากนั้นค่อยซ้อมงานหลายบทบาทใน [[AGENT-DEMO-QA]] ก่อนเก็บรายละเอียด UI

พาธในตารางเริ่มจาก `frontend/src/` ใช้เป็นแผนที่สำหรับรอบที่ใช้โค้ดได้ ตรวจ branch และไฟล์จริงอีกครั้งก่อนแก้

| ส่วน | จุดเริ่มอ่าน | สิ่งที่ต้องแยก |
|---|---|---|
| หน้าโครงการและแท็บ | `app/(dashboard)/assess/page.tsx` | ส่ง project และการทดลองปัจจุบันร่วมกันให้ Lab และ Nodes เก็บสถานะงานเหนืออายุของแท็บ |
| แชต | `components/three/skincare-lab/chat/LabAgentChat.tsx`, `useLabAgentChat.ts` ในโฟลเดอร์เดียวกัน | ใช้ composer, history, copy, voice และการสลับบทบาทเดิม เพิ่มผู้เขียน ผู้รับ และงานที่ข้อความนั้นอ้างถึง |
| รูปประจำตัว | `components/kit/app-header.tsx` กับ `frontend/public/images/lab-agents/` ใน repo | ใช้รูป session สำหรับผู้ใช้และรูปที่ตรงกับ role ID สำหรับ Agent ในเดโมออฟไลน์ใช้อักษรย่อ |
| ห้องและการเดิน | `components/three/skincare-lab/LabRoomExplorer.tsx`, `agents/workflow.ts`, `agents/agent.ts` ใต้ skincare-lab | นำทางและเล่นคลิปตามงานที่ถูกสร้างจากคำสั่ง หยุดวงเดินพื้นหลังที่แย่งควบคุมตัวเดียวกันในโหมดนี้ |
| ใบงานจำลองเดิม | `components/three/skincare-lab/agents/handoffDemo.ts` และ `chat/HandoffSheet.tsx` ใต้ skincare-lab | ใช้เนื้อหาตัวอย่างและ API การคลิกขวดได้ เลือกงานถัดไปจากคำสั่ง ผล และข้อจำกัดล่าสุด |
| รุ่นสูตร | `lib/lab-station/revision.ts`, `lib/lab-station/assessment.ts`, `components/formula/FormulaGraph.tsx` | การเปิด draft เดิมด้วยรหัส assessment แม่เพียงตัวเดียวไม่พอสำหรับสองกิ่ง ต้องระบุรุ่นลูกกับงานที่สร้างมัน |

## ลำดับและเวลาที่ใช้ตัดสินใจ

งบด้านล่างเป็นประมาณการ **แปดชั่วโมงสำหรับ FE คนเดียวเมื่อมีฐานเดิมพร้อม** รวมเวลาเชื่อมและตรวจในแต่ละช่วง การสร้างฉาก ตัวละคร และระบบแชตใหม่ทั้งหมดจากศูนย์ต้องประเมินเวลาอีกครั้ง

| ก่อน–หลัง | งาน | เวลา | หลักฐานที่ต้องเห็นก่อนไปต่อ |
|---|---|---:|---|
| 1 | กำหนด project, experiment, thread, task, sample และ event สร้างข้อมูลทดสอบสองโครงการ | 45 นาที | เหตุการณ์เดียวกันเข้าซ้ำสองครั้งแล้วมีงานเดียว อีกโครงการไม่มีข้อความหลุดมา |
| 2 | ทำแหล่งเหตุการณ์จำลองและการตีความคำสั่งในขอบเขต สั่งตรง ส่งต่อ ขอความชัดเจน เปลี่ยนเงื่อนไข และถามผล | 75 นาที | เริ่มจาก Analyst หรือ Researcher ได้ ผู้ช่วยตอบคำถามดูข้อมูลโดยไม่สร้างขวด จงใจทำส่งล้มเหลวและกู้ได้ |
| 3 | ต่อแชตส่วนตัว กลุ่ม รูปผู้ส่ง การตอบคำถาม และ checklist ใต้ข้อความ | 90 นาที | ตอนคนที่สามรับงาน ผู้ใช้ตามไปถึงข้อความเดียวกันในกลุ่ม ตอบส่วนตัวแล้วกลุ่มเห็นเฉพาะข้อสรุป |
| 4 | ต่อการเดิน ส่งขวด รับคำตอบเร็ว ป้ายเหนือหัว และคลิกตัวละคร | 75 นาที | ทดสอบคนละห้อง ปิดแชต หรือสลับไป Nodes ระหว่างเดินแล้วไม่ค้างหรือส่งซ้ำ |
| 5 | ต่อ Node อ่านอย่างเดียว รุ่นแม่–ลูก เงื่อนไขเผยแพร่ และข้อความสรุปของ Evaluator | 75 นาที | กิ่ง B เสร็จก่อน A แล้วขึ้นถูกชื่อ ขวดกับ Node อ่านผลเดียวกัน |
| 6 | เดินสองสถานการณ์เต็ม ทดสอบการกู้คืน เดโมบนจอแคบ แก้ปัญหาและซ้อมนำเสนอ | 120 นาที | ได้บันทึกผลตรวจจริงตาม [[AGENT-DEMO-QA]] และระบุรายการที่ยังรอทดสอบ |

ถ้าเวลาเริ่มเกิน ให้รักษาเส้นทาง “คำสั่ง → ผู้รับ → ผล → รุ่นสูตร” ไว้ก่อน ลดจำนวนบทพูดและรายละเอียดภาพเคลื่อนไหวได้ โดยคงสถานะส่งถึง ข้อมูลรายกิ่ง และการกู้คืนให้ตรวจได้

## ข้อมูลร่วมของทั้งสามหน้าจอ

ด้านล่างเป็น **ตัวอย่างภายใน FE** ชื่อฟิลด์พร้อมจับคู่สัญญาจริงของเพื่อนก่อนต่อ API

```json
{
  "eventId": "evt-018",
  "sequence": 18,
  "type": "handoff.accepted",
  "projectId": "demo-p1",
  "experimentId": "D01",
  "threadId": "demo-p1-group",
  "taskId": "review-v2b",
  "handoffId": "send-v2b-to-analyst",
  "from": "formulator",
  "to": "analyst",
  "formulaId": "d01-b",
  "parentFormulaId": "d01-root",
  "sourceMessageId": "user-07",
  "attempt": 2,
  "source": "demo"
}
```

- รหัสการส่งคงเดิมตลอดการลองซ้ำ รหัสเหตุการณ์แยกแต่ละเหตุการณ์ ผู้รับที่รับไปแล้วตอบรับงานเดิมได้ ใช้รหัสงานและรหัสขวดป้องกันการสร้างงานซ้ำ แม้ผู้ส่งพลาดคำตอบรับครั้งแรก
- เก็บเหตุการณ์แยกประเภทสำหรับส่งงาน รับงาน เริ่มหรือจบขั้นตอน ถามผู้ใช้ รับคำตอบ ปิดผลรายรุ่น และแนะนำรุ่น ข้อความมีรหัสผู้เขียนและผู้รับของตัวเอง การกด Copy หรือเปิดเธรดเก่าไม่มีผลข้างเคียงกับงาน
- เก็บสถานะจำลองแยกผู้ใช้ โครงการ และโหมด หากไม่มี login ให้สร้างขอบเขตผู้ใช้เดโมเฉพาะ เปลี่ยนโครงการแล้วงานเดิมต้องไม่เขียนทับหน้าที่เปิดอยู่ แยกผลจำลองออกจากประวัติ Assessment จริง
- ใบสูตรเป็น snapshot มีชื่อเดิมถาวร รหัสแม่ ส่วนผสม เหตุผล และผลสี่ด้าน ผลที่ยังประเมินไม่ได้เก็บเหตุผล ค่าที่ขาดยังคงเป็นค่าว่าง อ้างขวดด้วยรหัสรุ่นและการทดลองเมื่อเปิดย้อนหลัง

## ซิงก์คำตอบกับการเดิน

1. เมื่อผู้ส่งมอบหมายงาน บันทึกการส่งและแสดงข้อความทันที เริ่มเดินตามทางในฉาก
2. เหตุการณ์ผู้รับตอบรับ กับเหตุการณ์ตัวละครถึงจุดส่งของ มาได้คนละเวลา ถ้าคำตอบพร้อมก่อน ให้พักการแสดงคำตอบไว้แล้วเร่งการเดินอย่างนุ่มนวลในเพดานที่ตั้งได้ ทดลองเพดานด้วยระยะข้ามห้องและคลิปจริง
3. เมื่อรับงานสำเร็จและส่งถึงจุดหมายแล้วจึงแสดงคำตอบที่พักไว้ ถ้าเดินถึงก่อน ให้แสดงว่ารอรับงานจนการตอบรับมาถึง ระหว่างนั้นยังไม่สร้างผลสำเร็จ
4. ถ้าออกจาก Lab หรือใช้การลดการเคลื่อนไหว ให้ตัวควบคุมเดโมดำเนินการส่งตามเวลาจำลองได้โดยไม่ต้องรอเฟรมสุดท้ายของ WebGL กลับเข้าห้องแล้ววางตัวละครตามสถานะปัจจุบัน
5. ถ้าส่งล้มเหลวให้ลองซ้ำหนึ่งครั้ง เมื่อยังล้มเหลวให้ผู้ใช้ลองอีกครั้งเอง เหตุการณ์เก่าที่มาช้าไม่ย้อนสถานะงานที่สำเร็จแล้วหรือข้ามการตอบคำถาม

## ขอบเขตชิ้นส่วนที่จะส่งต่อ

แยกตัวจำลองเหตุการณ์กับนาฬิกา, ตัวสะสมสถานะโครงการ, รายการข้อความและรูปผู้ส่ง, ความคืบหน้ารายข้อความ, คำถามส่วนตัว, ตัวควบคุมการเคลื่อนไหว และตัวแปลงข้อมูลไป Nodes ออกจากกัน ให้แต่ละชิ้นรับข้อมูลผ่าน props หรือ interface ที่ระบุได้ เมื่อผ่าน QA ค่อยเก็บเวอร์ชันใน Obsidian พร้อมพาธต้นทาง ข้อมูลป้อน ตัวอย่างการใช้ dependency และหลักฐานทดสอบ เมื่อต่อ Backend เปลี่ยนจุดรับส่งเหตุการณ์ก่อน แล้วรันกรณีเดิมกับ API
