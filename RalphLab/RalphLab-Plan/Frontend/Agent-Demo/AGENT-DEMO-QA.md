# บทซ้อมและเกณฑ์ตรวจรับเดโม Agent

## ตรวจ Lab และรายการแชตเป็นอันดับแรก

1. เปิด Lab เลือก Analyst ส่ง “V1 มีอะไรบ้าง” ย้อนดูรายการแชต แล้วเปิด Analyst อีกครั้ง ต้องเห็นคำตอบเดิม และจำนวนงานกับขวดเป็นศูนย์ในเดโมใหม่
2. ส่ง “ช่วยตรวจสี่ด้านของ V1” ให้ Analyst ตรวจว่ามีงานของ Analyst และสรุปผลสมมติอยู่ในแชตส่วนตัว
3. เริ่ม “ทำสูตรลดสิวให้หน่อย” จาก Director โดยตรง แล้วเริ่มอีกโจทย์จาก Analyst เมื่อผู้รับผิดชอบคนที่สามรับงาน ให้เปิดกลุ่มจากลิงก์ในแชตเดิม และเปิดจากรายการแชต ทั้งสองทางต้องพาไปงานเดียวกัน
4. เปิดสมาชิกของแต่ละกลุ่ม ดูว่าใครรับงานแล้ว พิมพ์ถามความคืบหน้าในงานแรก ตรวจตัวอย่างข้อความล่าสุดและเวลาในรายการ และเปิดงานที่สองเพื่อยืนยันว่าข้อความไม่ข้ามงาน ลองซ้ำที่ความกว้าง 390 px
5. ก่อนนำเสนอ ระบุว่า checklist ไหนมาจากเหตุการณ์จริงในเดโม ผลไหนเป็น fixture และพฤติกรรมใดใน 3D หรือ Nodes ยังรอเชื่อม เก็บภาพ Before/After ตาม [[JAY-FRONTEND-BASELINE]]

ใช้กับเดโมที่สร้างตาม [[AGENT-DEMO-SPEC]] รายการด้านล่างเป็นกรณีที่ต้องรันหลังพัฒนา ฉากและค่าทั้งหมดเป็นข้อมูลสมมติสำหรับตรวจ UI

## บทซ้อม A · ผู้ใช้เปลี่ยนโจทย์ระหว่างงาน

| ทำอะไร | ควรเห็นอะไร |
|---|---|
| เปิดโครงการ P1 การทดลอง D01 เริ่มที่ Analyst พิมพ์ “ช่วยทำคลีนเซอร์สำหรับผิวเป็นสิวง่ายให้หน่อย” | Analyst รู้ว่างานครอบคลุมหลายบทบาท เชิญ Director ในแชตเดิม ผู้ใช้เห็นรูปกับชื่อของทั้งคู่ |
| Director ขอให้ Researcher ศึกษาเบส A/B | มีสามผู้รับผิดชอบ เริ่มใช้กลุ่ม P1 เพียงกลุ่มเดียว เธรดเดิมกดไปยังข้อความส่งต่อได้ |
| Researcher ส่งข้อเสนอให้ Formulator จากนั้น Formulator ส่งขวด V1 | สมมติ V1 มีน้ำ 84% กลีเซอริน 5% เบส A 10% น้ำหอม 1% คลิกขวดแล้วได้ D01/V1 เปิด Nodes ก่อนปิดผลเห็นสถานะรอ |
| ระหว่าง Analyst ตรวจ V1 พิมพ์ “ตั้งแต่รุ่นถัดไปไม่เอาน้ำหอม” | V1 ยังตรวจต่อด้วยสูตรเดิม ถ้าต้องยืนยันขอบเขตให้ถามส่วนตัว เลข 1 ค้างจนส่งคำตอบสำเร็จ กลุ่มเห็นข้อสรุป |
| ให้ทีมลองลด A และลอง B คนละทาง | V2-A มีน้ำ 87% กลีเซอริน 5% เบส A 8% ส่วน V2-B มีน้ำ 85% กลีเซอริน 5% เบส B 10% ทั้งคู่ชี้กลับ V1 สัดส่วนรวมรุ่นละ 100% |
| ตั้งให้ Analyst ปิดผล B ก่อน A แล้วสลับไป Nodes | เห็น V1 กับ V2-B ก่อน ข้อความและขวด A ยังรอผล เมื่อ A เสร็จชื่อ B ยังเหมือนเดิม |
| เปิดสรุปของ Evaluator | สมมติทั้งคู่ตรงข้อห้าม ผลผิวต่ำ แต่ผลตาของ B มีความเชื่อมั่นต่ำกว่า Evaluator อาจแนะนำ A เพื่อทบทวนต่อ ระบุข้อดีและข้อจำกัด พร้อมบอกว่าประสิทธิผลด้านสิวยังต้องมีหลักฐาน |

## บทซ้อม B · โมเดลให้ผลนอกขอบเขต

1. เปิด D02 ในโครงการเดิม งานเล็ก “ช่วยดูข้อจำกัดของผลนี้” เริ่มที่ Analyst และเข้าถึงข้อมูลของ D02 กลุ่ม P1 แยกบริบทของ D01 กับ D02 ได้แม้ทั้งคู่มี V1
2. จำลองผลพิษเฉียบพลันของ V1 ว่าอยู่นอกขอบเขต Analyst บันทึกเหตุผลในขั้นตอนที่สี่ ปิดการตรวจครบสี่ด้านได้ Node แสดง “สรุปไม่ได้ · นอกขอบเขต” ที่ endpoint นั้น
3. Evaluator ส่งประเด็นตรวจขอบเขตให้ Analyst และ Analyst นำผลไปหา Researcher ระหว่างนั้น Formulator เตรียมกิ่งที่เป็นอิสระ สลับแชตแล้วกลับมาดูได้ว่าใครรับงานไหน
4. ตั้งให้ Researcher พบเพียงหลักฐานเดิม ต้องเห็นเหตุผลที่หยุดค้นและคำถามถึงผู้ใช้ เช่น “จะเก็บผลนี้ไว้เทียบเฉพาะด้านที่มีข้อมูล หรือส่งผู้เชี่ยวชาญทบทวน?” เปิดคำถามทิ้งไว้แล้วสังเกตว่างานอีกกิ่งเดินต่อ
5. ตอบในแชตส่วนตัว กลุ่มได้รับข้อสรุปหนึ่งครั้ง Evaluator อธิบายว่าด้านใดเทียบได้ ด้านใดยังค้าง หากหลักฐานยังแยกรุ่นไม่ได้ ให้จบโดยไม่ติดป้ายแนะนำ

## กรณีที่บัคมักซ่อนอยู่

| กรณีทดสอบ | ถือว่าผ่านเมื่อ |
|---|---|
| งานเดี่ยว / สองคน / สามคน | หนึ่งคนตอบเอง สองคนคุยต่อในเธรดเดิม คนที่สามจึงย้ายงานเข้ากลุ่ม การเปิดอ่านโดย Agent อีกตัวไม่เพิ่มจำนวนผู้รับผิดชอบ |
| คำถามเทียบกับคำสั่ง | “ใน V1 มีน้ำหอมไหม” อ่านผลโดยจำนวนสูตรเท่าเดิม “ลองสูตรไม่มีน้ำหอมอีกทาง” จึงสร้างกิ่งเมื่อไม่เกินเพดาน ข้อความกำกวมให้ถามเจาะจง |
| คำตอบมาภายในครึ่งวินาที ผู้ส่งอยู่คนละห้อง | เห็น “ส่งแล้ว” ทันที เดินเร็วขึ้นอย่างต่อเนื่องตามทาง มีการส่งของ คำตอบผู้รับแสดงหลังถึงและตอบรับ เวลาเปิดแชตยังพิมพ์หรือลอกข้อความได้ |
| เดินถึงก่อนรับคำตอบ / สลับแท็บ / ลดการเคลื่อนไหว | สถานะรอถูกต้อง กลับมาแล้วไม่มีการเดินหรือพิมพ์ซ้ำเพื่อสร้างงานใหม่ เวอร์ชันและข้อความมีชุดเดียว |
| แผน B ของหน้าตา checklist | Agent สองคนมีงานพร้อมกัน แต่ละรายการอยู่ใต้ข้อความเจ้าของงาน กดพับของคนหนึ่งไม่พับอีกคน จำนวนขั้นที่เสร็จตรงกับเหตุการณ์และไม่เพิ่มทุกเฟรม |
| เปิดคำถามแล้วปิด / ตอบซ้ำ / ตอบข้อความอื่น | เลขแดงค้างหลังเปิดอ่าน หายหลังตอบคำถามถูก ID และได้รับการบันทึก กลุ่มได้รับเฉพาะข้อสรุปหนึ่งครั้ง |
| ทำการตอบรับครั้งแรกหล่นหลังผู้รับสร้างงานแล้ว | ผู้ส่งลองซ้ำอัตโนมัติหนึ่งครั้ง ผู้รับส่งการตอบรับของงานเดิม จำนวนงาน ขวด Node และข้อความรับงานต่อรหัสเดิมเท่ากับหนึ่ง |
| ตั้งให้ล้มเหลวทั้งสองครั้ง แล้วปิดและเปิดแชต | ปุ่ม “ลองอีกครั้ง” ยังอยู่ที่ข้อความเดิม กดแล้วใช้รหัสเดิม งานกิ่งอื่นไม่ค้าง เมื่อสำเร็จปุ่มหาย |
| สร้าง V2 ไว้ก่อน แล้วจึงขอทางเลือกที่สอง | ข้อความเก่า ขวด และ Node ยังเรียก V2 เหมือนเดิม ส่วนกิ่งใหม่ชื่อ V2-B รหัสแม่ของทั้งคู่คือรหัส V1 เดียวกัน |
| ไม่มีผล / โหลดพลาด / ขาด domain หรือ confidence | แยกกำลังรอ โหลดพลาด และข้อมูลไม่พอได้ เปิดผังตัวอย่างด้วยตัวเองได้ ผลจำลองไม่ปะปนกับ Assessment จริง |
| สองการทดลองในกลุ่มเดียว / สลับโครงการ / รีโหลด | หน้าห้องและ Nodes เปิดการทดลองที่เลือกไว้ รหัสแยกได้แม้ชื่อ V1 เหมือนกัน ไม่มีเหตุการณ์หรือภาพผู้ใช้ข้ามโครงการหรือบัญชี |
| มือถือ 390px / แชตแคบ / Google ไม่มีรูป | ผู้ส่ง ผู้รับ ข้อความยาว ปุ่มตอบ และข้อจำกัด endpoint อ่านได้ ใช้อักษรย่อแทนรูปได้ ขอบแชตไม่บัง Agent |

## สิ่งที่ต้องเก็บเพื่อให้คนอื่นตรวจซ้ำได้

บันทึกชื่อสถานการณ์ คำสั่งที่พิมพ์ ลำดับเหตุการณ์จริง รหัสงานและขวด จำนวนงานก่อน–หลัง retry และภาพสามจังหวะ (กำลังส่ง / รับแล้ว / ผลขึ้น Node) ระบุผลผ่านหรือตกเป็นรายกรณี แยกผลทดสอบต้นแบบแบบกดทีละขั้น ผลทดสอบเดโมในฉาก 3D และผลทดสอบ API เมื่อเชื่อมจริง
