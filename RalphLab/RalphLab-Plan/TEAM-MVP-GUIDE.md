# RalphLab · คู่มือโครงการสำหรับทีม

ฉบับออกแบบ MVP ของทีม วันที่ 20 พฤศจิกายน 2569 สำหรับผู้พัฒนา ผู้ทดสอบ และผู้นำเสนอในงาน Sea x OpenAI Regional Codex Hackathon Thailand วันที่ 21 พฤศจิกายน 2569

**เป้าหมายเดโม** จบหนึ่งโครงการตั้งแต่รับโจทย์ ส่งใบงานจริงอย่างน้อยหนึ่งครั้ง พักข้อสรุปเมื่อข้อมูลไม่พอ แล้วเปิด V1 เทียบกับ V2-A ให้เห็นว่าเปลี่ยนอะไร เพราะหลักฐานใด และใครตัดสินใจ สมาชิกคนที่ 2 อ่าน [[MEMBER-02-FE-DELIVERY]] สำหรับลำดับทำหน้าจอและเกณฑ์รับงาน

## โจทย์และสิ่งที่ผู้ใช้ได้รับ

นักพัฒนาสูตรทำความสะอาดต้องเลือกว่าจะส่งสูตรใดไปทดลองต่อ แต่ผลคัดกรอง เอกสารวัตถุดิบ และข้อจำกัดของลูกค้าอยู่คนละที่ RalphLab เก็บเรื่องเหล่านี้ไว้ใน **โครงการทดลอง** เดียว ผู้ใช้เปิดดูสูตรแต่ละรุ่น ใบงานที่ส่งต่อ หลักฐาน ผลรายด้าน และคำถามที่ยังต้องทดลองจริงได้

ข้อความที่ต้องปรากฏในทุกหน้าที่แสดงผล รวมถึงกราฟเปรียบเทียบและแผงผลในห้องแล็บ

> ผลคัดกรองด้วยคอมพิวเตอร์ โปรดยืนยันด้วยวิธีทดสอบที่เหมาะสมก่อนนำไปใช้จริง

**ฐาน RalphGuard ตามแผนทีม** มีเว็บกรอกสูตร ตรวจ SMILES ด้วย RDKit และคัดกรองด้วย QSAR สี่ด้าน ได้แก่ ระคายเคืองผิว ระคายเคืองตา แพ้สัมผัส และพิษเฉียบพลันทางปาก การแสดงผลของ run ต้องยึดขอบเขตและช่องทางรับสัมผัสที่แหล่งผลนั้นระบุ หาก run เดิมระบุเพียง “พิษเฉียบพลัน” ให้คงข้อความนั้นและบอกว่าขาดข้อมูลช่องทางรับสัมผัส

**งาน RalphLab ที่วางแผนไว้** คือ Agent ที่ส่งใบงาน ระบบเหตุการณ์ที่ขับห้อง CCTV และกราฟ คลังความรู้ และการเชื่อม eLabFTW ส่วนที่มีให้ลองใน sandbox กับส่วนที่ยังต้องเชื่อมระบุไว้ใน [[MEMBER-02-FE-DELIVERY]]

## เดินโครงการตัวอย่างหนึ่งรอบ

1. **ตั้งโจทย์** เปิดโครงการ “ลดข้อกังวลด้านการระคายเคืองของสูตรทำความสะอาด” ล็อกสาร A ระบุสารที่ปรับได้ เกณฑ์รายด้าน และงบทดลองเพิ่มสองรุ่น ผู้ใช้เลือกได้ว่าจะให้ดำเนินการภายในขอบเขตเอง หรือขออนุมัติก่อนสร้างสูตรใหม่ทุกครั้ง
2. **สร้าง V1** Study Lead ออกใบงาน Formulation Chemist บันทึกส่วนผสม หน้าที่ สัดส่วนที่รวมได้ 100% และสมมติฐาน ผู้ใช้คลิกขวดเพื่อเปิดรุ่นสูตรนั้น
3. **เปิดผลสี่ด้าน** Computational Toxicologist รับตัวอย่างที่สถานีคัดกรอง ผู้ใช้คลิกหลอดผลเพื่อดู endpoint สารที่เกี่ยวข้อง รุ่นโมเดล คะแนน ความเชื่อมั่น และ applicability domain ต้องแสดงผลระดับสารและวิธีรวมเป็นผลของสูตรกำกับด้วย
4. **ส่งปัญหาให้ถูกคน** ถ้าผลด้านผิวเกินเกณฑ์และมีหลักฐานตรงด้าน ให้นักเคมีเสนอ V2-A ถ้าหลักฐานตอบคนละ endpoint ให้ Chemical Data Curator ตรวจเพิ่มและแสดง unknown ระหว่างรอ ถ้าพบข้อจำกัดของโมเดลซ้ำหลายเคส ให้เปิดใบงานพัฒนาโมเดลแยกต่างหาก การเปลี่ยนสารที่ล็อกต้องรอคำตัดสินจากผู้ใช้
5. **เปรียบเทียบและจบงาน** เปิด V1 เทียบ V2-A ดูสารและสัดส่วนที่เปลี่ยน ผลดีขึ้นหรือแย่ลง รวมถึงด้านที่ยังเปรียบเทียบไม่ได้ จะเพิ่ม V2-B เป็นลูกของ V1 เพื่อเปลี่ยนปัจจัยคนละตัวก็ได้ เก็บ V1 ไว้เสมอ ปิดโครงการเมื่อถึงเกณฑ์ หมดงบ หรือพบคำถามที่ต้องทดลองจริง พร้อมบันทึกเหตุผล

## เจ้าหน้าที่ห้าบทบาท

| เจ้าหน้าที่ | ใช้อะไรตัดสินใจ | สิ่งที่ส่งให้คนถัดไป |
|---|---|---|
| Study Lead | ใบโจทย์ ข้อจำกัด งบ และแนวทางแผนการศึกษาของ OECD GLP | ใบงาน เกณฑ์หยุด คำขออนุมัติ และบันทึกการตัดสินใจ |
| Formulation Chemist | หน้าที่ของสารจาก EPA Safer Choice และเอกสารเทคนิคของผู้ผลิต ตรวจสารที่ล็อกกับสัดส่วนก่อนสร้างรุ่นลูก | สูตรรุ่นลูก รายการเปลี่ยนแปลง และสมมติฐาน ประสิทธิภาพการทำความสะอาดต้องมีผลทดสอบของตนเอง |
| Computational Toxicologist | OECD IATA, NICE/ICE ตามชื่อในแผนทีม และ model card ของรุ่นที่รัน ตรวจขอบเขตโมเดลและหลักฐานของ endpoint เดียวกัน | ผลคัดกรองรายด้าน ความไม่แน่นอน และเหตุผลที่ใช้ผลหรือพักข้อสรุป |
| Chemical Data Curator | PubChem PUG REST เพื่อตรวจตัวตนสาร และรายงานการทดลองต้นทางเพื่ออ่านชนิดการทดสอบกับความหมายของ label | ระเบียนรหัสสาร endpoint ผล ต้นทาง และข้อจำกัด บันทึก unknown เมื่อหลักฐานไม่พอ |
| QSAR Model Scientist | OECD QSAR Assessment Framework, รายงาน validation และสคริปต์ RalphGuard ตรวจสัดส่วนคลาส สารซ้ำ และชุดกันไว้ | รายงานเปรียบเทียบ candidate กับรุ่นใช้งาน การเลื่อนรุ่นโมเดลต้องมีการตัดสินใจแยกจากโครงการสูตร |

## ข้อมูล QSAR ที่ทีมอ้างและกฎรับหลักฐาน

ตรวจตัวเลขในแผนกับไฟล์ที่ Git commit `488ac126` แล้ว คอลัมน์ production เป็นจำนวน positive/negative ในรายงาน validation ส่วน PubChem เสริมเป็นจำนวนโครงสร้างเฉพาะของไฟล์ curated แต่ละ endpoint การ์ดผลของผู้ใช้ต้องใช้ผลจาก run ของสูตรที่เปิดอยู่

| Endpoint | รายงาน production บวก / ลบ | PubChem เสริม บวก / ลบ | แหล่งเสริมที่ทีมระบุว่ามี experimental negative |
|---|---:|---:|---|
| ระคายเคืองผิว | 38 / 58 | 160,560 / 0 | 216 |
| ระคายเคืองตา | 44 / 63 | 169,274 / 0 | 1,045 |
| แพ้สัมผัส | 30 / 56 | 8,359 / 0 | HPPT มี negative 859 และ positive 78 รวม 937 โครงสร้างที่ผ่านการคัด |
| พิษเฉียบพลัน | 29 / 52 | 119,389 / 0 | แผนไม่ได้ระบุจำนวน |

ตรวจย้อนหลังได้ด้วย `git show 488ac126:<path>` โดยใช้ `scientific/models/validation_report.json`, `data/curated/pubchem_verified_manifest.json`, `data/curated/experimental_negative_manifest.json` และ `data/curated/sens_hppt_import_report.json` ไฟล์ `data/curated/pubchem_verified_{skin,eye,sens,acute}.csv` ที่ commit นี้มีเฉพาะ label 1

ก่อนเทรน ให้ผู้รับผิดชอบนับใหม่หลังตรวจสารซ้ำ label ขัดแย้ง และข้อมูลที่ทับซ้อนกับชุดทดสอบ ช่องว่างกับผลลบคนละ endpoint ต้องคงสถานะ unknown ที่ commit ดังกล่าว `scripts/train_candidate_v2.py` คำนวณเพดานอัตรา positive ต่อ negative ภายในเงื่อนไขที่เปิดเพดานจำนวนแถวและข้อมูลเกินเพดานนั้น แต่ค่าเริ่มต้นของเพดานจำนวนแถวคือ 0 ให้สมาชิกคนที่ 1 ทดสอบกรณีค่าเริ่มต้นก่อนเทรน บันทึกจำนวนที่เข้าเทรนจริงแยก endpoint พร้อม sensitivity, specificity และ confusion matrix บนชุดที่กันไว้

## ห้อง CCTV กราฟ และประวัติ

กล้องครอบคลุมสถานีรับโจทย์ โต๊ะพัฒนาสูตร และสถานีคัดกรอง การมอบหมายจากระบบเป็นจุดเริ่มท่าเดิน การประเมินเสร็จเป็นจุดเปิดหลอดผล เจ้าหน้าที่เปิดใบงานล่าสุด ประวัติผู้ส่งและผู้รับ เครื่องมือ หลักฐาน และเหตุผลสั้น ๆ ได้ ขวดเปิดสูตรรุ่นเดียวกันในกราฟ กราฟและรายการงานต้องใช้ได้เมื่อปิดภาพ 3D

ออกแบบตัวละครและ rig ใน Blender ส่งออกโมเดลสำหรับเว็บ ตรวจ idle, walk และการรับส่งขวดบนเครื่องเดโม รอยแดงหรือชั้นผิวที่แสดงเป็นภาพประกอบต้องมีคำกำกับ ใช้เฉพาะด้านที่โมเดลรองรับ

## สถาปัตยกรรมและข้อมูลกลางตามแบบทีม

Next.js และ TypeScript แสดงห้องผ่าน React Three Fiber และกราฟผ่าน React Flow ฝั่ง FastAPI ตรวจสิทธิ์และข้อจำกัดก่อนเรียกเครื่องมือ บริการ Python, RDKit และ scikit-learn คืนผลคัดกรอง Neon PostgreSQL เก็บสถานะและประวัติ ตามแบบให้งาน OpenAI แยกตามบทบาทและส่งเฉพาะใบงาน หลักฐาน และคู่มือที่เกี่ยวข้อง จุดเชื่อมของเดโมปัจจุบันดูในแผน FE

| ข้อมูล | สิ่งที่ต้องตามกลับได้ |
|---|---|
| Project | เจ้าของ โจทย์ เกณฑ์ งบ และสิทธิ์ |
| FormulaVersion | รุ่นแม่ ส่วนผสม สัดส่วน และเหตุผลที่สร้างรุ่นนี้ |
| WorkOrder | ผู้ส่ง ผู้รับ สถานะ และทางออกเมื่องานติดขัด |
| Run | รุ่นสูตร endpoint รุ่นโมเดล ผลและความไม่แน่นอน |
| Evidence | ต้นทาง วิธีทดลอง endpoint และรุ่นข้อมูล |
| Decision | ผู้อนุมัติ คำขอ รุ่นสูตร และขอบเขตที่อนุมัติ |

ทุกเหตุการณ์มี `event_id`, `project_id`, `version_id` และเวลา การส่งซ้ำต้องเกิดผลครั้งเดียว เมื่อเปิดหน้าใหม่ให้สร้างภาพจากสถานะที่บันทึกในฐานข้อมูล งานค้างและ API ภายนอกล้มเหลวต้องแสดงเหตุและใช้รหัสงานเดิมเมื่อลองใหม่ คำอนุมัติใช้ได้เฉพาะคำขอและรุ่นที่แสดง

## คลังความรู้และระบบภายนอก

ข้อเสนอของทีมคือสร้าง private repo ชื่อ `ralphlab-knowledge` ให้ทั้งสี่คน clone ด้วย GitHub Desktop แล้วเปิดเป็น Vault ใน Obsidian ให้ pull ก่อนแก้ และ commit/push หลังแก้ กฎวิทยาศาสตร์ต้องผ่านผู้ดูแลเนื้อหาก่อนรวมเข้า main

| โฟลเดอร์ที่เสนอในคลังทีม | ใช้เก็บ |
|---|---|
| `roles/` | หน้าที่และสิทธิ์ของ Agent |
| `sources/` | ที่มา วันที่ และขอบเขตการใช้ข้อมูล |
| `procedures/` | กฎตัดสินใจและการส่งต่อ |
| `cases/` | เคสตัวอย่างสำหรับฝึกใช้และซ้อมเดโม |
| `assets/` | ภาพประกอบกับลิงก์ไปยังไฟล์ 3D และน้ำหนักโมเดลที่มีเลขรุ่น |
| `evals/` | ข้อสอบและเฉลย แยกจากดัชนีที่ Agent ค้นได้ |

ใบงานเก็บ path และ commit ของโน้ตที่ใช้ eLabFTW เป็นจุดเชื่อม REST API สำหรับเปิดบันทึกการทดลองและส่งรายงานแต่ละรุ่น ให้เก็บรหัสบันทึกภายนอกคู่กับ `run_id` หากเขียนล้มเหลวให้เก็บผลใน Neon และแสดงรอส่งซ้ำ เดโมใช้ชุดข้อมูล EPA และ NICE/ICE ที่กำกับวันที่ ส่วน LINE และ Telegram เป็นช่องทางแจ้งเตือนระยะถัดไป

## ใครส่งอะไรให้ใคร

| สมาชิก | งานที่รับผิดชอบ | จุดรวมงาน |
|---|---|---|
| 1 · Agent และวิทยาศาสตร์ | ระบบ Agent กฎตัดสินใจ และการเชื่อม QSAR | ส่งตัวอย่างเหตุการณ์ V1 → ใบงาน → V2 และข้อมูลกรณีพัก/ขออนุมัติ ให้ FE ใช้ตั้งแต่ต้น |
| **2 · Frontend และ 3D** | โมเดล rig กล้อง CCTV แชต รายการงาน แผงผล และกราฟ | ส่งหน้าที่เลือกเจ้าหน้าที่ ขวด และสูตรในกราฟจาก `event_id` เดียวกันได้ พร้อมมุมดูข้อมูลเมื่อปิด 3D |
| 3 · ทดสอบและคู่มือ | ทดสอบสถานการณ์จากเคสพร้อมเฉลยของผู้ดูแลวิทยาศาสตร์ | ส่งขั้นตอน ผลที่คาด ผลจริง และภาพพร้อมรหัสเหตุการณ์เมื่อพบปัญหา |
| 4 · เดโมและส่งมอบ | โครงการตัวอย่าง สไลด์ บทพูด วิดีโอสำรอง และเอกสาร | รับโครงการที่ทดสอบแล้ว ลิงก์หลักฐาน และ commit ที่นำเสนอได้ |

| webhook หรือคำสั่งซ้ำ | เกิด V2 หนึ่งรุ่นและเห็นการส่งมอบหนึ่งครั้ง |
| รีเฟรชระหว่างงาน | ใบงาน กราฟ และขวดคืนสู่สถานะเดียวกัน เหตุการณ์ที่ทำเสร็จแล้วไม่เริ่มซ้ำ |

**ลำดับส่งงาน** เดิน workflow จริงให้ครบหนึ่งรอบ → ผูก 3D กับกราฟเข้ากับเหตุการณ์เดียวกัน → เชื่อมสมุดแล็บ → ทดสอบกรณีล้มเหลว → ซ้อมและจับเวลา

**สิ่งที่เปิดให้กรรมการดู** สำหรับ Deep Domain AI เปิดหลักฐานสอง endpoint แล้วอธิบายเหตุที่แทนกันไม่ได้ สำหรับ Autonomous & Adaptive AI ให้เห็นการเลือกผู้รับงานใหม่และการหยุดรอเมื่อเกินอำนาจ สำหรับ AI-Native Operations เปิดการตัดสินใจเดียวกันในใบงาน ห้อง 3D และสมุดแล็บ เก็บ commit และเคสทดสอบของงานที่พัฒนาด้วย Codex ระหว่างการแข่งขันประกอบการนำเสนอ
