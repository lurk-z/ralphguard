PART 1 — ข้อมูล RalphGuard ที่มีอยู่จากบริบทเดิม

หมายเหตุสำคัญ:
ข้อมูลในส่วนนี้คือสิ่งที่ผู้ใช้เคยเล่าไว้ในการสนทนาก่อนหน้า ไม่ใช่ผลจากการตรวจ repository ปัจจุบัน รายละเอียดเชิงเทคนิค ฟีเจอร์จริง โครงสร้างข้อมูล และสถานะการทำงาน ต้องตรวจสอบจากโค้ดในเครื่องก่อนสรุป ห้ามถือว่าสิ่งที่กล่าวไว้ด้านล่างยังทำงานอยู่ครบถ้วนในเวอร์ชันปัจจุบัน

1. ภาพรวมโครงการ
- ชื่อโครงการเดิม: RalphGuard
- โครงการเคยเข้ารอบ Finalist ของ NSC 2026 ตามข้อมูลที่ผู้ใช้เคยแจ้ง
- เป็นแพลตฟอร์มเกี่ยวกับการประเมิน/แสดงข้อมูลด้านการระคายเคืองหรือความเป็นพิษ (irritation / toxicity)
- แนวคิดสำคัญที่ผู้ใช้เคยอธิบายคือการนำเสนอผลหรือข้อมูลที่เกี่ยวข้องกับการระคายเคือง/ความเป็นพิษ โดยไม่ใช้การทดลองกับสัตว์ (non-animal irritation/toxicity platform)
- ข้อมูลที่มีอยู่ยังไม่เพียงพอจะยืนยันว่าโครงการใช้วิธีทดสอบ มาตรฐานทางวิทยาศาสตร์ โมเดล AI หรือแหล่งข้อมูลใดอยู่จริง จึงต้องตรวจสอบจาก source code, เอกสารใน repository และข้อมูลที่ผู้ใช้จะให้เพิ่มเติม
- ในเวอร์ชันที่ผู้ใช้เคยอธิบาย ไม่มีระบบ Login และ Register

2. สิ่งที่จำได้เกี่ยวกับการนำเสนอผลและ UI

- ยังไม่ยืนยันจากบริบทเดิมว่า Day 1/3/7 หมายถึงการจำลองการเปลี่ยนแปลงของผิว การแสดงผลหลังได้รับสาร หรือเป็นเพียงลำดับภาพประกอบ ต้องตรวจจากโค้ดและคำอธิบายผลิตภัณฑ์จริง

4. ข้อจำกัดและเป้าหมายรอบใหม่
- ผู้ใช้ต้องการตั้งหัวข้อ/ทิศทางใหม่ชื่อ “Ralph Lab” (คำว่า “raplh lab” ในข้อความเดิมน่าจะหมายถึง “Ralph Lab”)

- ต้องการให้วิเคราะห์ว่าควรเพิ่มอะไร และอะไรมีคุณค่าต่อการแข่งขัน

- ต้องประเมินอย่างจริงจังว่าแต่ละแนวคิดสามารถทำเสร็จภายในเวลานี้ได้หรือไม่ โดยอิงจากโค้ดเดิม ไม่ใช่ประเมินจากการเริ่มเขียนใหม่
- ผู้ใช้จะเล่ารายละเอียดและเงื่อนไขการแข่งขันเพิ่มเติมภายหลัง ดังนั้นอย่าแต่งโจทย์การแข่งขัน กติกา เกณฑ์คะแนน หรือกลุ่มเป้าหมายขึ้นเอง
- จุดประสงค์คือให้ได้ข้อเสนอที่นำไปวิเคราะห์/คัดเลือกต่อได้ ไม่ใช่รีบเลือกไอเดียแล้วเริ่มแก้โค้ดทันที

5. ข้อมูลที่ยังไม่มีหลักฐานเพียงพอและห้ามสมมติ

- รายชื่อสาร/ผลิตภัณฑ์ที่รองรับ

- มีระบบผู้ใช้/สิทธิ์ในส่วนอื่นหรือไม่ แม้เวอร์ชันที่เคยเล่าจะไม่มี Login/Register

PHASE 1 — ตรวจสอบ Repository ก่อน brainstorm
------------------------------

1. ตรวจสอบโครงสร้างโปรเจกต์จาก root path จริง
2. อ่านไฟล์สำคัญก่อน เช่น README, package.json, lockfile, configuration, route definitions, app entry points, environment examples, API/service layer และเอกสารภายใน
3. สำรวจโฟลเดอร์และไฟล์ โดยให้ความสำคัญกับ:
   - frontend pages/routes/layouts
   - components และ shared UI
   - features/modules ที่เกี่ยวข้องกับ RalphGuard
   - state management และ data flow
   - API client, services, hooks และ mock data
   - backend/server functions (ถ้ามี)
   - database schema, ORM, migrations หรือ data models (ถ้ามี)
   - 3D model, Three.js/React Three Fiber หรือส่วน render ใบหน้า (ถ้ามี)
   - chart, visualization, result interpretation และ report/export (ถ้ามี)
   - assets, images, icons, fonts และ design tokens
   - tests, lint, build scripts และ deployment configuration
4. ตรวจดู Git status และ branch ได้เพื่อทำความเข้าใจสถานะ แต่ห้าม reset, checkout, clean, commit, push หรือแก้ไขไฟล์ใด ๆ ในขั้นตอนสำรวจ
5. ห้ามเปิดเผยค่า secret จาก .env หรือ credentials ในคำตอบ หากพบให้ระบุเพียงว่ามี environment variable ที่จำเป็น โดยไม่แสดงค่า
6. ห้ามสรุปจากชื่อไฟล์เพียงอย่างเดียว ให้เปิดอ่านไฟล์ที่เกี่ยวข้องและตาม data flow จริง
7. ตรวจสอบคำสั่ง build/test/lint ที่มีอยู่ และพิจารณารันเฉพาะคำสั่งที่ปลอดภัย ไม่ทำให้ข้อมูลหรือสภาพแวดล้อมเปลี่ยนแปลง
8. ถ้าเข้าถึง path ไม่ได้ ห้ามแสร้งว่าตรวจแล้ว ให้แจ้งข้อจำกัดตรง ๆ และขอให้ผู้ใช้เปิดโฟลเดอร์/แนบไฟล์/ส่ง tree listing ตามความจำเป็น

หลังตรวจเสร็จ ให้ทำ “Repository Reality Check” โดยแยกข้อมูลเป็น 4 กลุ่ม:
A. Implemented and working — มีโค้ดและตรวจพบว่าใช้งานได้
B. Implemented but unverified/broken — พบโค้ด แต่ยังยืนยันการทำงานไม่ได้ หรือมีจุดผิดพลาด
C. Partially implemented — มีบางส่วน แต่ flow ยังไม่ครบ
D. Not found — ไม่พบใน repository

สำหรับทุกข้อสรุปสำคัญ ให้ระบุ path ของไฟล์ และชื่อ component/function/route/schema ที่เกี่ยวข้อง เพื่อให้ผู้ใช้ย้อนตรวจได้ ห้ามแต่งชื่อไฟล์หรือโครงสร้างที่ไม่มีอยู่จริง

PHASE 2 — สรุป RalphGuard ในสถานะปัจจุบัน
------------------------------

สร้างภาพรวมระบบที่อ่านเข้าใจได้ โดยตอบคำถามต่อไปนี้:
1. RalphGuard แก้ปัญหาอะไร และผู้ใช้เป้าหมายที่อนุมานได้จากผลิตภัณฑ์คือใคร (แยกข้อเท็จจริงจากข้ออนุมาน)
2. User journey ปัจจุบันตั้งแต่เริ่มใช้งานจนได้ผลลัพธ์เป็นอย่างไร
3. มีหน้า/โมดูลอะไรบ้าง แต่ละหน้าทำหน้าที่อะไร
4. ข้อมูลไหลจากจุดใดไปจุดใด และมีแหล่งข้อมูลจริงหรือ mock data
5. ฟีเจอร์ใดเป็นจุดเด่นที่มีอยู่แล้วและสามารถนำมาต่อยอดได้
6. จุดอ่อน/ข้อจำกัดด้าน UX, UI, technical architecture, data credibility, performance และ reliability มีอะไรบ้าง
7. ส่วนใดพร้อมใช้ ส่วนใดต้องซ่อมก่อน และส่วนใดไม่ควรแตะเพราะเสี่ยงทำระบบเดิมพัง
8. มี dependency, integration หรือ technical debt ใดที่อาจทำให้การพัฒนา 8 ชั่วโมงไม่เป็นไปตามแผน

ทำตารางสรุปอย่างน้อยมีคอลัมน์:
- Module/Feature
- Current behavior
- Evidence (file path + component/function)
- Status (Working / Partial / Broken / Not found / Unverified)
- Reuse potential
- Risk/constraint

PHASE 3 — กำหนดโจทย์และทิศทาง Ralph Lab
------------------------------

ให้คิดว่า Ralph Lab เป็นชื่อหัวข้อหรือทิศทางการต่อยอดจาก RalphGuard แต่ยังไม่ต้องฟันธงความหมายของคำว่า Lab เอง ให้เสนอความเป็นไปได้หลายทิศทาง โดยเชื่อมโยงกับแกนเดิมของ RalphGuard และสิ่งที่ repository ทำได้จริง

ให้ brainstorm อย่างน้อย 5–8 แนวคิดที่แตกต่างกันอย่างมีนัยสำคัญ ตัวอย่างหมวดที่สามารถพิจารณาได้ (เป็นเพียงกรอบช่วยคิด ไม่ใช่ข้อกำหนดว่าต้องทำทั้งหมด):
- Lab สำหรับทดลอง/จำลอง/เปรียบเทียบผล
- Lab สำหรับสำรวจข้อมูลสารและความเสี่ยง
- Lab สำหรับแสดงผลการระคายเคืองหรือ toxicity ในรูปแบบที่เข้าใจง่าย
- Lab สำหรับเปรียบเทียบสารหรือสูตรหลายแบบ
- Lab สำหรับติดตามผลตามช่วงเวลา เช่น Day 1/3/7 หากข้อมูลรองรับอย่างถูกต้อง
- Lab สำหรับอธิบายหลักฐานหรือที่มาของผลประเมิน (explainability / evidence)
- Lab สำหรับสร้างรายงานหรือสรุปผลให้ผู้ใช้/กรรมการเข้าใจ
- Lab สำหรับ workflow ของนักวิจัยหรือผู้ประเมิน

ห้ามเสนอแค่เปลี่ยนสี เปลี่ยน layout หรือเพิ่มหน้า Dashboard โดยไม่มีคุณค่าด้านผลิตภัณฑ์ที่ชัดเจน
ห้ามอ้างว่าสามารถทำนายผลทางวิทยาศาสตร์ได้ หากไม่มีโมเดล/ข้อมูล/วิธี validation รองรับ
ห้ามใช้คำว่า AI, simulation, prediction หรือ scientific validation เพื่อการตลาด หากในระบบไม่ได้ทำสิ่งนั้นจริง
หากเสนอข้อมูลจำลองเพื่อ demo ต้องระบุชัดเจนว่าเป็น simulated/demo data ไม่ใช่ผลการทดลองจริง

สำหรับแต่ละแนวคิด ให้ระบุ:
1. ชื่อแนวคิด
2. ปัญหาที่แก้
3. ผู้ใช้เป้าหมาย
4. คุณค่าที่เพิ่มจาก RalphGuard เดิม
5. User flow แบบสั้น ตั้งแต่เริ่มจนเห็นผล
6. หน้าจอ/ฟีเจอร์ที่ต้องเพิ่มหรือแก้
7. ส่วนของโค้ดเดิมที่นำกลับมาใช้ได้ พร้อม file path
8. สิ่งที่ต้องสร้างใหม่
9. ข้อมูล/API/model ที่ต้องใช้ และมีอยู่แล้วจริงหรือไม่
10. ความเสี่ยงและ dependency
11. MVP ที่เล็กที่สุดซึ่งยังสื่อคุณค่าได้
12. สิ่งที่ตัดออกได้เพื่อให้เสร็จใน 8 ชั่วโมง
13. ผลกระทบที่คาดหวังต่อผู้ใช้และต่อการแข่งขัน โดยแยกเหตุผลออกจากการคาดเดา

PHASE 4 — ประเมิน Impact และความเป็นไปได้ภายใน 8 ชั่วโมง
------------------------------

ประเมินทุกแนวคิดจากเงื่อนไขจริงว่าเหลือเวลาพัฒนา 1 วัน 8 ชั่วโมง และต้องต่อยอดจาก codebase ปัจจุบัน

ใช้เกณฑ์คะแนน 1–5 พร้อมอธิบายเหตุผล:
- User Impact: ผู้ใช้ได้ประโยชน์จริงมากแค่ไหน
- Competition Impact: ทำให้ผลงานโดดเด่น/สื่อสารคุณค่ากับกรรมการได้มากแค่ไหน
- Feasibility: ทำเสร็จได้จริงใน 8 ชั่วโมงมากแค่ไหน (คะแนนสูง = ทำได้ง่าย/มีโอกาสเสร็จสูง)
- Reuse: นำของเดิมกลับมาใช้ได้มากแค่ไหน
- Demo Value: สาธิตให้เห็นความแตกต่างได้ชัดแค่ไหน
- Technical Risk: ความเสี่ยงทางเทคนิค (คะแนนสูง = เสี่ยงมาก)
- Scientific/Data Risk: ความเสี่ยงจากข้อมูลหรือการกล่าวอ้างเกินหลักฐาน (คะแนนสูง = เสี่ยงมาก)

อย่ารวมคะแนนแบบกลบความเสี่ยงสำคัญ ให้แสดงคะแนนทุกมิติแยกกัน และจัดประเภท:
- Quick win: มีโอกาสเสร็จสูงและเห็นคุณค่าชัด
- Stretch: ทำได้ถ้า scope แคบและไม่มี blocker
- Too risky: ไม่ควรเลือกสำหรับเวลานี้

ให้ระบุระดับความมั่นใจของ estimate ด้วย โดยอิงจากการตรวจโค้ด หากยังไม่ได้รันระบบหรือทดสอบ end-to-end ต้องแจ้งว่าเป็น estimate เบื้องต้น

คำนวณเวลาของแต่ละแนวคิดโดยแจกแจงงานเป็นชั่วโมง เช่น:
- สำรวจ/ยืนยัน flow ที่เกี่ยวข้อง
- UI/UX design adjustment
- Frontend implementation
- Data/API integration
- Error/empty/loading states
- Testing and bug fixing
- Demo preparation

เวลารวมต้องไม่เกิน 8 ชั่วโมง รวมเวลาทดสอบและแก้บั๊กด้วย อย่าใช้เวลา 8 ชั่วโมงไปกับการเขียนฟีเจอร์ทั้งหมดโดยไม่เผื่อทดสอบ

------------------------------
PHASE 5 — คัดเลือกแนวทางที่เหมาะสม
------------------------------

หลังเปรียบเทียบ ให้เสนอ:
1. แนวทางที่แนะนำเป็นอันดับ 1 พร้อมเหตุผลที่อิง codebase
2. ตัวเลือกสำรองอันดับ 2 ในกรณีเจอ technical blocker
3. แนวทางที่ไม่ควรทำในรอบนี้ พร้อมเหตุผล
4. Feature scope แบบ Must have / Should have / Could have / Won't have
5. สิ่งที่ไม่ควรแก้ในระบบเดิมเพื่อจำกัด regression risk
6. Definition of Done ที่ตรวจสอบได้ ไม่ใช้คำกว้าง ๆ เช่น “UI สวยขึ้น” หรือ “ระบบดีขึ้น”
7. เกณฑ์ยอมรับงาน เช่น flow ไหนต้องคลิกได้ ข้อมูลใดต้องแสดงถูกต้อง และกรณีผิดพลาดต้องแสดงอย่างไร

ให้แนะนำเพียง 1 แนวทางหลักที่มีขอบเขตพอดีกับ 8 ชั่วโมง ไม่ควรเลือกหลายแนวทางจนทำไม่จบ

------------------------------
PHASE 6 — แผนลงมือทำแบบ 8 ชั่วโมง
------------------------------

ทำแผนพัฒนาแบบ timebox รวม 8 ชั่วโมง แนะนำให้แบ่งเป็นช่วงที่ตรวจความคืบหน้าได้ เช่น:
- 0:00–0:45 ยืนยัน scope และสำรวจโค้ดเฉพาะจุด
- 0:45–1:30 วาง flow/UI และเตรียม data contract
- 1:30–4:30 พัฒนาฟีเจอร์แกนหลัก
- 4:30–5:30 เชื่อมข้อมูลและจัดการ states
- 5:30–6:45 ทดสอบ flow และแก้บั๊ก
- 6:45–7:30 ปรับ UX และ responsive/presentation
- 7:30–8:00 เตรียม demo และตรวจ Definition of Done

เวลาข้างต้นเป็นตัวอย่าง ต้องปรับตามงานจริง ห้ามยึดตารางตัวอย่างหากไม่เหมาะกับ scope

แต่ละช่วงต้องบอก:
- งานที่ต้องทำ
- ไฟล์/โมดูลที่คาดว่าจะต้องแตะ (เฉพาะที่ตรวจพบจริง)
- ผลลัพธ์เมื่อจบช่วง
- วิธีตรวจว่าผ่าน
- ความเสี่ยงที่อาจทำให้ล่าช้า

กำหนด Stop-loss rule ด้วย เช่น หาก API หรือ data model ไม่พร้อมภายในเวลาที่กำหนด ให้สลับไปใช้ fallback ที่ซื่อสัตย์ต่อผู้ใช้และไม่แสดงข้อมูลจำลองเป็นข้อมูลจริง

------------------------------
PHASE 7 — มุมมองการแข่งขันและการนำเสนอ
------------------------------

วิเคราะห์ว่าแนวทางที่แนะนำจะเล่าให้กรรมการเข้าใจได้อย่างไร โดยไม่แต่งเกณฑ์การแข่งขันที่ผู้ใช้ยังไม่ได้ให้

ให้เสนอ:
- Problem statement แบบกระชับ
- Solution statement
- จุดแตกต่างจาก RalphGuard เดิม
- Demo storyline 2–3 นาที
- หน้าจอหรือ interaction ที่ควรโชว์เป็นลำดับ
- หลักฐานที่ควรเตรียมเพื่อยืนยันว่า feature ทำงานจริง
- ข้อจำกัดที่ควรเปิดเผยอย่างตรงไปตรงมา
- สิ่งที่ยังไม่ควรกล่าวอ้างทางวิทยาศาสตร์

อย่าประเมินโอกาสชนะเป็นเปอร์เซ็นต์ และอย่าอ้างว่า impact สูงโดยไม่มีเหตุผลรองรับ

------------------------------
PHASE 8 — รูปแบบคำตอบที่ต้องส่งกลับ
------------------------------

จัดทำผลลัพธ์ตามลำดับนี้:

A. Executive Summary
สรุปสถานะ RalphGuard และข้อเสนอ Ralph Lab ใน 1 หน้าจอโดยประมาณ

B. Repository Map
โครงสร้างโฟลเดอร์ที่สำคัญ พร้อมอธิบายหน้าที่ของแต่ละส่วน โดยอ้างอิง path จริง

C. Current Feature Audit
ตารางฟีเจอร์ที่มีอยู่จริง สถานะ และหลักฐานในโค้ด

D. Current User Journey & Architecture
สรุป user flow และ data flow พร้อมระบุจุดที่เป็น mock/real/unverified

E. Opportunity Areas
พื้นที่ที่ RalphGuard สามารถพัฒนาต่อยอดเป็น Ralph Lab ได้

F. Ralph Lab Brainstorm
แนวคิด 5–8 แบบ พร้อมรายละเอียดและ mapping กับโค้ดเดิม

G. Impact × Feasibility Matrix
ตารางคะแนนทุกมิติ พร้อมเหตุผลและความมั่นใจของ estimate

H. Recommended Direction
ข้อเสนออันดับ 1, ตัวเลือกสำรอง และแนวทางที่ควรตัดออก

I. 8-Hour Execution Plan
แผนรายช่วงเวลา งานที่ต้องทำ ผลลัพธ์ และวิธีตรวจ

J. Demo & Competition Story
เรื่องเล่าสำหรับ demo และหลักฐานที่ควรเตรียม

K. Open Questions for the User
รวบรวมเฉพาะคำถามที่จำเป็นจริง ๆ และยังตอบไม่ได้จาก repository เช่น โจทย์การแข่งขัน เกณฑ์คะแนน กลุ่มเป้าหมาย และรายละเอียดที่ผู้ใช้ตั้งใจให้ Ralph Lab เป็นอะไร

L. First Action
ระบุสิ่งแรกที่ควรทำหลังผู้ใช้อนุมัติแนวทาง โดยระบุไฟล์ที่ต้องแก้และเหตุผล แต่ยังไม่ต้องแก้ไฟล์จนกว่าผู้ใช้จะสั่ง

------------------------------
กติกาการทำงาน
------------------------------

- เริ่มจากอ่านและวิเคราะห์ ห้ามแก้โค้ดทันที
- ห้ามสร้างไฟล์ แก้ไข ลบ ย้าย ติดตั้ง dependency หรือรัน migration โดยไม่ได้รับคำสั่งจากผู้ใช้
- ห้ามเปลี่ยน architecture หรือ refactor ใหญ่ในงานที่มีเวลา 8 ชั่วโมง
- ห้ามสมมติว่าฟีเจอร์มีอยู่เพียงเพราะเคยมีในคำอธิบายเก่า
- ทุกข้อเสนอควรเชื่อมกับ path, component, function, route หรือ data structure ที่ตรวจพบจริง
- แยก Fact / Inference / Assumption ให้ชัดเจน
- ถ้าข้อมูลไม่พอ ให้บอกว่าไม่พบหรือยังยืนยันไม่ได้ แทนการคาดเดา
- คิดแบบต่อยอดจากของเดิม ใช้ reuse ให้มากที่สุด
- ให้ความสำคัญกับ end-to-end demo ที่ทำงานได้จริง มากกว่าจำนวนฟีเจอร์
- เผื่อเวลาทดสอบและแก้บั๊กเสมอ
- หากพบว่าความสามารถหลักด้าน toxicity/irritation ยังไม่มีข้อมูลหรือ validation ห้ามทำให้ UI สื่อว่าผลลัพธ์นั้นเป็นผลทางวิทยาศาสตร์ที่ผ่านการรับรองแล้ว
- ให้ตอบเป็นภาษาไทย ใช้ศัพท์เทคนิคภาษาอังกฤษได้ตามความเหมาะสม
- อธิบายตรงไปตรงมา ไม่ต้องเห็นด้วยกับทุกไอเดียของผู้ใช้ หากไอเดียใดไม่เหมาะกับเวลา 8 ชั่วโมงให้บอกชัดเจน
- เป้าหมายคือข้อเสนอที่มีโอกาสทำเสร็จจริง มี impact ที่อธิบายได้ และ demo ได้อย่างน่าเชื่อถือ
