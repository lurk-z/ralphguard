# Prompt สำหรับ Claude · Ralph Lab FE demo

## Copy from here

Build a Thai-language frontend demonstration of Ralph Lab, a multi-agent cosmetic formulation workspace. One developer owns the FE. Work from this brief and materials created or expressly supplied for this run. The backend team will later connect real agents. Deliver an interactive demo that works without an API key. Mark simulated conversations, evidence and endpoint results as demo data. Use React and TypeScript with three project tabs: Assessment, Nodes and Lab.

Assessment shows formula name, ingredients and percentages, a screening control, and results for four endpoints with uncertainty and applicability. Keep assistant conversations in Lab. For Lab use a lightweight low-poly cutaway room, gray square tiles, a wide middle room, two side rooms connected through partition openings, two central benches, a sample station, fridge and bin. Fit the room into the remaining width beside chat, support orbit and zoom, focus the selected agent on first click and return smoothly on close. Start with simple reusable meshes when an animated asset is unavailable. Track the five roles, four endpoint trays and versioned vials separately. Clicking a tray reveals its endpoint outcome. After viewing a sample's result let the user keep or discard it. Keeping it makes the vial inspectable in fridge storage; discarding removes it from physical inventory while the completed experiment remains in history. Label placeholders and simulated results accurately. Improve broad responsive coverage, login and landing visuals after the primary experiment passes end to end.

### What the audience should be able to do

Begin on the competition checkout of `jay-frontend`. Record the starting commit and capture the original project tabs and room entry at the same viewport you will use for After. Check permission for prepared code independently from permission for prepared art. If only models are supplied, wire the supplied room and five character GLBs using fresh frontend code. If models are unavailable, use simple geometric stand-ins and a role picker. The first milestone is an actual typed command in Lab, followed by the selected agent's reply in that thread. Test the workflow before spending time on styling.

A user can click any of five agents and type a short Thai request. Each agent answers within its role. The Director owns the brief and constraints, the Researcher owns evidence and alternatives, the Formulation Scientist owns versioned recipes and sample vials, the Analyst owns endpoint screening and model applicability, and the Evaluator owns trade-offs and recommendations. A small request finishes with the chosen agent. Route a new multi-role goal to the Director. Recognize a bounded set of free-text intents including asking about an existing result, commissioning a formula, changing a constraint, requesting evidence and comparing variants. Ask a specific clarifying question on ambiguous input. Let the user type a reply or select an answer. A read request alone must create zero new formulas.

### Conversation design

Use a LINE-style inbox inside the Lab panel. Show a private agent's portrait, English role, latest message and time. Show each promoted job as its own inbox row with a task name and member portraits. Derive the name from the user's brief in the offline simulation. Accept the agent-provided title when connected. Key conversations by stable IDs so two jobs with similar names keep independent messages. Inside a group let the user inspect its assigned members, ask about that job, return to the inbox, and reopen it at the same job. Place a small muted speaker name beside the avatar, aligned to the message column. Keep names readable on a narrow screen.

1. Keep one group conversation per project. A single participant works in its individual thread. A second assigned agent may join that thread. On the third distinct assigned agent for that job, continue it in the existing project group and leave a navigable pointer in the original conversation. Keep the experiment visible beside each job. Private tasks remain available after the group forms.
2. Use a white, uncluttered chat panel alongside the room. Show each agent's portrait and English role name at speaker changes. Right-align user messages with the signed-in user's Google session photo and use initials on image failure or in an anonymous demo. Preserve the room's visible center when the panel opens, closes or resizes.
3. Show concise, explicit handoffs, for example “Researcher → Formulation Scientist · ขอสูตรตั้งต้น D01”. Record the sender, recipient, experiment, linked message, task and any sample ID. Show sent, accepted, working and completed as distinct states. Use an expandable progress checklist immediately under the responsible agent's message. Each task owns its own checklist, even when several people work concurrently. Update the original message in place. Show observable operations such as retrieving a fixture, checking an endpoint, or saving a version. Drive each checkmark from a completed operation.
4. Above each agent use plain, unboxed text. During an actual wait show “thinking...”. During work show a short action. A pending question takes precedence and shows a red 1 with an accessible label. Clicking it opens the relevant question in that agent's private chat. Opening the message leaves it pending. Once an answer is successfully recorded, clear the indicator and publish only the decision to the project group. Continue unrelated work during the wait.

### Event delivery and the room

Keep role selection in the chat header and open recent conversations inside the panel. For history deletion, the first click changes the trash icon to a check in the same spot; the second click deletes that conversation. On message hover or keyboard focus reveal the timestamp and a fixed-size copy button; offer the same action on touch. Switch the icon to a check on copy success without changing bubble width. Animate only a newly arriving reply. Reopening an old thread shows the saved text immediately. During voice input show a listening state and a waveform; indicate when the microphone is unavailable. Use a resizable split: as the chat changes width, keep the lab centered within the remaining space.

Build a deterministic local event source behind a replaceable interface. Scope it by user, project, experiment and demo mode above the lifetime of either view. Each handoff has a stable ID, an attempt count, and distinct events for sending and acceptance. Preserve chronology and deduplicate redeliveries and late acknowledgements. Drive chat, room movement, vial inspection and Nodes from this same state. Keep the demo store separate from live assessments.

Show “sent” immediately and begin a walk along a valid route. If the simulated recipient answers quickly, buffer the reply, accelerate the walk and gait together up to a natural configurable cap, then reveal it when both delivery and acceptance have occurred. If the walk finishes first, show that the sender is waiting for acceptance. A hidden room or reduced-motion preference must still allow logical delivery. On return, reconcile positions and outstanding work from current state. Preserve orbit, camera focus, and agent/sample selection if extending an existing scene.

Automatically retry a failed handoff once with the same handoff/task identity. If it fails again, expose a manual retry on the existing chat message. Test loss of the acknowledgement after the recipient already created the task. Duplicate delivery must yield the original receipt and must create no extra sample, acceptance message, job or node. Do not let a late duplicate error downgrade a delivered job.

### Formula history and Nodes

Save immutable snapshots for V1 and at most two children in the demo. A change requested after V1 was submitted applies to later versions. Preserve the decision message, parent ID, actual ingredient differences and reason. Preallocate V2-A and V2-B for simultaneous branches. If a single child was already called V2, keep that name forever and call the later alternative V2-B.

Default Nodes to the experiment selected in Lab. Include an experiment selector. Before the first result, show the current real demo status and an explicit button to view a separate labeled example. Publish an actual experiment node only after the Analyst has closed all four endpoints, each with a result or an explicit inconclusive reason. Endpoints are skin irritation, eye irritation, contact sensitization and acute toxicity. Show confidence, missing evidence and applicability limits where relevant. Never interpret a missing or out-of-domain value as low risk.

Arrange version groups by depth from top to bottom. Each group has one wide version card with its name, parent, changes, problems and endpoint outcomes, with separate ingredient cards below, up to four per row. Each card shows the substance name and percentage and may show structure/SMILES when available. Curved gray arrows point upward from ingredients to their own version. State parentage on the card, with no extra version-to-version edge. Support canvas pan, zoom, minimap on larger screens and dragging for layout. Keep formula data read-only here. After the Evaluator recommends a version, show one advantage and one limitation on the card and link to the full recommendation in group chat. Recommend only when constraints and evidence support it. Allow “insufficient evidence to choose”.

### Build order and proof of completion

1. Open Lab, select any agent and send a Thai command using the composer. Connect the reply to a project-scoped event store. Verify the selected private conversation receives it, including when starting directly with the Director. Then test duplicate events, acknowledgement loss, late messages and isolation of projects. Add immutable versions and stable branch names when the workflow reaches formula creation.
2. Connect private and group chat, profile photos, per-message progress and private questions. Demonstrate a one-agent request, a two-agent request, and a job promoted on the third agent.
3. Connect station travel, visible work, sample identity and delivery timing. Use a half-second reply from across the room to test a long walk, then repeat while switching tabs.
4. Feed Nodes from the same experiment. Make branch B finish before A and prove that the published label, parent and endpoint limitations still match the right vial.
5. Rehearse two selectable scenarios from start to recommendation. In scenario A the user adds a fragrance restriction after V1. Keep V1 unchanged and test two children. In scenario B an endpoint is outside its model domain. Return it to the Analyst for an applicability review, send the evidence gap to the Researcher, continue an independent branch and ask the user only when a choice is needed. Stop on a satisfied goal, the demo limit, or a blocker requiring user judgment. These four risk endpoints do not establish acne-treatment efficacy.
6. Run the primary flows at desktop and 390px width. Track visible evidence at sent, accepted and result publication. Report what was actually exercised, any placeholder, and what remains unverified. Keep reusable chat, progress, avatar, agent status, handoff, room bindings and lineage components individually documented, with inputs, integration paths and a usage example after they pass. Once the demo is accepted, map the event interface to the backend team's actual contract and run the same tests again.
