# แผนปรับปรุงหน้า `/projects`

สถานะเอกสาร: Implementation เสร็จแล้ว รอตรวจด้วยข้อมูลจริงจำนวนมากเพิ่มเติม

Branch ที่ตรวจ: `main-Responsive/UI`

ขอบเขต: หน้าโปรเจกต์ทั้งหมด, Create/Edit/Delete Project, Responsive และ Motion
ยังไม่แก้หน้า `/assess` ในงานชุดนี้

## 1. เป้าหมาย

- ทำให้หน้า `/projects` ดูเป็นระบบงานระดับมืออาชีพและไม่โล่งเกินไป
- ให้ `/projects` เป็นหน้าหลักหน้าเดียวของระบบจัดการโปรเจกต์ในช่วงนี้
- สร้างโปรเจกต์ด้วย Create View เต็มพื้นที่ และแก้ไขผ่าน Dialog โดยไม่เปลี่ยน route
- เพิ่มสีและไอคอนประจำโปรเจกต์ โดยยังคงภาพลักษณ์ทางการแพทย์
- แจ้งผล Create/Edit/Delete/Restore ผ่าน Toast ที่ชัดเจน
- รองรับ Undo Delete โดยไม่ทำให้ผลประเมินสูญหายถาวรก่อนผู้ใช้มีโอกาสย้อนกลับ
- รองรับ Mobile, Tablet และ Desktop โดยไม่มี horizontal overflow
- เพิ่ม Motion ที่สื่อความหมายและรองรับ `prefers-reduced-motion`

## 2. Skill ที่ใช้วิเคราะห์

- `ui-ux-pro-max`
  - Accessibility และ keyboard navigation มาก่อนความสวย
  - Touch target อย่างน้อย 44px
  - หนึ่งหน้าควรมี Primary CTA หลักเพียงหนึ่งตำแหน่ง
  - ใช้ Lucide/SVG แทน Emoji
  - ใช้ semantic color tokens และไม่ใช้สีเป็นตัวสื่อความหมายเพียงอย่างเดียว
  - Micro-interaction ควรอยู่ประมาณ 150–300ms
  - Undo เหมาะกับ destructive action
- `gsap-core`, `gsap-react`, `gsap-performance`
  - ใช้ `transform`, `opacity` และ `autoAlpha`
  - หลีกเลี่ยงการ animate `width`, `height`, `top`, `left`
  - Animation ต้อง cleanup เมื่อ component unmount
  - รองรับ `prefers-reduced-motion`
- `gsap-plugins`
  - ใช้ `Flip` สำหรับการเพิ่ม ลบ และจัดตำแหน่ง Project Card ใหม่

หมายเหตุ: search script ของ `ui-ux-pro-max` ใน repository เป็น pointer ไปยัง path ที่ไม่มีอยู่ จึงใช้ checklist จาก `SKILL.md` โดยตรงแทน

## 3. วิเคราะห์ UI ปัจจุบัน

### สิ่งที่ดีอยู่แล้ว

- ใช้ shadcn/ui สำหรับ Card, Dialog, AlertDialog, Button และ Form
- ใช้ Lucide icons
- มี Loading skeleton, Empty state และ Error handling
- Project Card ใช้ keyboard เปิดได้
- API มี Create, Edit และ Delete แล้ว
- มี Sonner Toaster และ GSAP ใน dependencies

### ปัญหาหลัก

1. Sidebar มีเพียงเมนู “โปรเจกต์” ซึ่งซ้ำกับหน้าที่กำลังเปิดและทำให้ฝั่งซ้ายดูว่าง
2. Empty state กว้างและสูงมาก ทำให้หน้าดูเหมือนยังออกแบบไม่เสร็จ
3. Create Project แยกไป `/projects/new` ทั้งที่ปัจจุบันมี destination หลักเพียงหน้าเดียว
4. Create/Edit ยังไม่มีตัวเลือกสีและไอคอนประจำโปรเจกต์
5. Edit สำเร็จยังไม่มี Success Toast
6. Delete ปัจจุบันเป็น Hard Delete และลบ Assessment ผ่าน ORM cascade จึง Undo ด้วย Toast อย่างเดียวไม่ได้
7. Project Card ยังแยกเอกลักษณ์แต่ละโปรเจกต์ได้น้อย
8. Motion ของ Card, Dialog และการเปลี่ยนข้อมูลยังไม่เป็นระบบเดียวกัน

## 4. การตัดสินใจด้านโครงสร้าง

### 4.1 ใช้ Sidebar สำหรับ Brand และ Navigation

หน้า `/projects` ใช้ Sidebar แบบกระชับ ประกอบด้วย:

- Logo และชื่อ RalphGuard
- เมนู “โปรเจกต์ทั้งหมด”
- เส้นขอบที่ลากเพื่อปรับความกว้างได้ และเปลี่ยนเป็น icon-only เมื่อย่อ

เหตุผล:

- แยก Brand และ Navigation ออกจากเครื่องมือจัดการรายการ
- Top App Bar เหลือข้อมูลและเครื่องมือที่สัมพันธ์กับหน้าปัจจุบัน
- รองรับการเพิ่ม navigation จริงในอนาคตโดยไม่สร้างเมนูปลอม

`/projects` ใช้ `ProjectsShell` เฉพาะหน้า ส่วนหน้าลึกยังใช้ shell เดิมตามโครงสร้างปัจจุบัน

### 4.2 ให้ Create/Edit อยู่ใน route เดียว

- ปุ่ม “สร้างโปรเจกต์” เปลี่ยนพื้นที่เนื้อหาเป็น `ProjectCreateView`
- Create View แสดงข้อมูลหลักก่อน แล้วจึงแสดงสีและไอคอน
- ปุ่มแก้ไขยังเปิด `ProjectFormDialog` ในโหมด Edit
- `/projects/new` ไม่แสดงใน navigation
- Route เดิมควร redirect กลับ `/projects` หรือคงเป็น compatibility route ชั่วคราว

### 4.3 ไม่เพิ่มเมนูหรือหน้าที่ระบบยังไม่มี

ยังไม่เพิ่ม Dashboard, Recent, Archive หรือ Settings ใน sidebar เพื่อเติมพื้นที่ เพราะจะสร้าง navigation ที่ไม่มีการใช้งานจริง

## 6. Project Card

แต่ละ Card แสดง:

- Icon ประจำโปรเจกต์บนพื้นสีอ่อน
- ชื่อโปรเจกต์
- คำอธิบายไม่เกิน 2 บรรทัด
- วันที่สร้างหรือแก้ไขล่าสุด
- ปุ่ม Edit และ Delete
- เปิดโปรเจกต์ด้วยการคลิก Card ทั้งใบ

แนวทางสี:

- เลือกจาก preset เท่านั้น ไม่ใช้ unrestricted color picker
- ตัวเลือก 10 สี: Teal, Cyan, Blue, Indigo, Violet, Emerald, Amber, Slate, Rose, Orange
- ใช้สีเป็น accent ของ icon, border หรือแถบเล็ก ไม่เปลี่ยนพื้น Card ทั้งใบเป็นสีสด
- Selected color ต้องมี check icon เพื่อไม่พึ่งสีเพียงอย่างเดียว

แนวทาง icon:

- ใช้ Lucide ชุดเดียวกับระบบ
- ตัวเลือก 10 แบบ: `FlaskConical`, `Beaker`, `TestTube2`, `Microscope`,
  `ShieldCheck`, `Droplets`, `Atom`, `Leaf`, `HeartPulse`, `ClipboardCheck`
- ทุก icon-only button ต้องมี `aria-label` และ Tooltip

## 7. Create View และ Edit Dialog

ใช้ `ProjectCreateView` สำหรับการสร้างแบบเต็มพื้นที่ และใช้ `ProjectFormDialog`
สำหรับแก้ไขข้อมูลเดิม

ลำดับข้อมูล:

1. ชื่อโปรเจกต์และคำอธิบายเป็นข้อมูลหลัก
2. สีและไอคอนเป็นข้อมูลเสริม
3. ปุ่มยกเลิกและสร้างอยู่ท้าย flow

พฤติกรรม:

- Focus ช่องชื่อเมื่อเปิด
- Validate ชื่อเมื่อ blur และเมื่อ submit
- Enter submit เมื่อ focus อยู่ในช่องชื่อ
- ปิด Dialog ไม่ได้ระหว่าง request
- ปุ่ม Save/Create มี Loading state
- Error แสดงใกล้ form และมี `role="alert"`

Toast copy:

- Create: `สร้างโปรเจกต์ “{name}” สำเร็จ`
- Edit: `แก้ไขโปรเจกต์ “{name}” สำเร็จ`
- Error: ระบุสาเหตุและสิ่งที่ผู้ใช้ทำต่อได้

## 8. Undo Delete ที่ถูกต้อง

### ปัญหาปัจจุบัน

`DELETE /projects/{id}` ลบ Project จริงทันที และ relationship ใช้ `cascade="all, delete-orphan"` จึงอาจลบ Assessment ทั้งหมดด้วย การนำ Project object กลับมาเฉพาะ Frontend จะไม่สามารถกู้ Assessment เดิมได้

### แนวทางที่เลือก: Soft Delete

Backend:

1. เพิ่ม `deleted_at` ในตาราง `projects`
2. `DELETE /projects/{id}` เปลี่ยนเป็นตั้งค่า `deleted_at`
3. `GET /projects` ไม่คืนโปรเจกต์ที่ถูกลบ
4. เพิ่ม `POST /projects/{id}/restore`
5. ยังไม่ลบ Assessment ตอน Soft Delete
6. เตรียม Hard Delete/Purge เป็นงานแยกในอนาคต

Frontend:

1. ผู้ใช้ยืนยัน Delete ผ่าน AlertDialog
2. ซ่อน Card หลัง Backend Soft Delete สำเร็จ
3. แสดง Toast:
   - ข้อความ: `ลบโปรเจกต์ “{name}” แล้ว`
   - Action: `Undo`
4. เมื่อกด Undo ให้เรียก Restore API และนำ Card กลับตำแหน่งเดิม
5. แสดง `กู้คืนโปรเจกต์แล้ว`
6. ถ้า Restore ล้มเหลว แสดง Error Toast พร้อม Retry

Workspace ใน `localStorage` ต้องไม่ถูกลบทันทีตอน Soft Delete เพื่อให้ Undo กลับมาได้ครบ การ cleanup ถาวรต้องทำตอน Purge เท่านั้น

## 9. Backend/Data Model ที่ต้องเพิ่ม

ฟิลด์ Project:

- `color_key`: string enum พร้อม default `teal`
- `icon_key`: string enum พร้อม default `flask`
- `updated_at`: datetime
- `deleted_at`: nullable datetime

API:

- Create รับ `color_key`, `icon_key`
- Update รับ `color_key`, `icon_key`
- ProjectOut ส่งค่าทั้งสองกลับ
- Delete เป็น Soft Delete
- Restore endpoint
- List/Get ต้องไม่คืน deleted project

Validation:

- Backend whitelist สีและ icon
- Frontend และ Backend ใช้ key ชุดเดียวกัน
- ห้ามรับ raw CSS/hex/icon component name จากผู้ใช้โดยตรง

## 10. Motion Specification

ใช้ Motion เท่าที่สื่อเหตุและผล:

| เหตุการณ์ | Animation | เวลา |
|---|---|---:|
| เปิด Dialog | Fade + `y: 8` + `scale: 0.98 → 1` | 220ms |
| ปิด Dialog | Fade + scale เล็กน้อย | 150ms |
| โหลด Project Grid ครั้งแรก | Card fade + `y: 10`, stagger 35ms | 220–280ms |
| สร้างโปรเจกต์ | Card ใหม่ fade/scale เข้า + highlight ring ชั่วคราว | 260ms |
| แก้ไขสีหรือ icon | Crossfade preview และ accent | 180ms |
| ลบโปรเจกต์ | Card fade + `scale: 0.98` | 160ms |
| Undo | Card กลับตำแหน่งเดิมด้วย Flip | 220ms |
| Reflow ของ Grid | GSAP Flip | 220–260ms |

ข้อกำหนด:

- ใช้ transform/opacity เท่านั้นใน motion หลัก
- จำกัด stagger ไม่ให้รายการจำนวนมากรอนาน
- Animation ต้อง interruptible
- `prefers-reduced-motion: reduce` ปิด stagger, translate และ scale เหลือ state change ทันทีหรือ fade สั้น
- Cleanup GSAP context/tween ทุกครั้งเมื่อ unmount

3. เปลี่ยน Delete เป็น Soft Delete
4. เพิ่ม Restore API
5. เพิ่ม Backend tests สำหรับ Create/Edit/Delete/Restore และ Assessment preservation

เหตุผล: หากทำ Undo Toast ก่อน Soft Delete ผู้ใช้อาจเห็นว่าย้อนกลับได้ แต่ข้อมูล Assessment ถูกลบไปแล้ว

1. สร้าง `ProjectsShell`
2. สร้าง Sidebar สำหรับ Brand, Navigation และ Resize handle
3. สร้าง Top App Bar สำหรับข้อมูลหน้า Search และ Layout switch
4. กำหนด content max-width, gutters และ breakpoints
5. ตรวจ mobile header และ safe spacing

### P2 — Create View และ Edit Form

1. สร้าง `ProjectCreateView`
2. ใช้ `ProjectFormDialog` สำหรับ Edit
3. ย้าย Create มาอยู่ใน `/projects` โดยเปลี่ยน content state
4. เพิ่ม Color Selector
5. เพิ่ม Icon Selector
6. เพิ่ม Create/Edit Success Toast
7. ทำ `/projects/new` เป็น compatibility redirect

### P3 — Project Grid และ Page States

1. ปรับ Project Card
2. เพิ่ม Search และเรียงล่าสุดอัตโนมัติ
3. ทำ Empty state ให้กระชับและอยู่กึ่งกลาง content
4. ปรับ Loading skeleton ให้ตรงกับ Card จริง

### P4 — Delete + Undo

1. ใช้ AlertDialog ยืนยันการลบ
2. เรียก Soft Delete
3. แสดง Toast พร้อม Undo action
4. เรียก Restore เมื่อกด Undo

### P5 — Motion

1. Dialog motion
2. Card entrance
3. Create/Edit feedback
4. Delete/Undo และ Grid reflow ด้วย GSAP Flip
5. Reduced-motion fallback

### P6 — Accessibility และ Responsive QA

1. Keyboard navigation
2. Focus management หลังเปิด/ปิด Dialog
3. Screen reader labels และ Toast `aria-live`
4. Touch targets อย่างน้อย 44px
5. Contrast ของทุก project color
6. ทดสอบ 375/768/1024/1440px
7. ทดสอบชื่อและคำอธิบายยาว
8. ทดสอบ 0, 1, 10 และ 50+ โปรเจกต์

### 15.1 เป้าหมายผู้ใช้

ผู้ใช้หลักคือนักวิจัยหรือผู้พัฒนาผลิตภัณฑ์ skincare ที่ต้องการ:

- เห็นทันทีว่ากำลังทำงานในโปรเจกต์และสูตรใด
- เข้าใจขั้นตอนถัดไปโดยไม่ต้องเดาจากปุ่มที่ disabled
- ตรวจสูตรและสัดส่วนสารก่อนนำไปทาบนพื้นที่จำลอง
- ระบุตำแหน่งทาบนโมเดลก่อนส่งสูตรประเมิน
- แยกสถานะ “ยังไม่ทา”, “พร้อมประเมิน”, “กำลังวิเคราะห์” และ “มีผลแล้ว” ได้ชัดเจน
- เปรียบเทียบหลายสูตรบนโมเดลเดียวกันโดยข้อมูลไม่ปะปน
- กลับเข้าหน้าหรือกด F5 แล้วทำงานต่อจากสถานะเดิมได้

### 15.2 Workflow หลักที่ต้องเปลี่ยน

Workflow เดิม:

`เลือกโปรเจกต์ → สร้างสูตร → เพิ่มสาร → ประเมิน → ทาโมเดล → ดูผล → F5`

Workflow ใหม่ที่ต้องใช้:

`เลือกโปรเจกต์ → สร้างสูตร → เพิ่มสาร → ทาโมเดล → ประเมิน → ดูผล → F5`

ขั้นตอนภายในหน้า `/assess`:

1. **เลือกหรือสร้างสูตร**
   - ต้องมีสูตรที่เลือกอยู่หนึ่งสูตร
   - สูตรแต่ละกล่องเป็นการทดลองอิสระ แต่รอยของทุกสูตรสามารถแสดงบนโมเดลพร้อมกันได้
2. **เพิ่มและตรวจสาร**
   - ต้องมีสารอย่างน้อย 1 รายการ
   - ตรวจ SMILES, ความเข้มข้น, สารซ้ำ และผลรวมไม่เกิน 100%
   - น้ำฐานยังคำนวณอัตโนมัติเหมือนเดิม
3. **ทาสูตรบนโมเดล**
   - เปิดการทาครีมสีขาวทันทีเมื่อสูตรผ่านการตรวจพื้นฐาน โดยไม่ต้องมีผลประเมินก่อน
   - รอยทาต้องผูกกับ `formulaId`
   - สูตรต่างกันห้ามทาทับตำแหน่งเดียวกัน
   - ยางลบลบรอยสีขาวได้ก่อนประเมิน และมีทั้ง “ล้างรอยที่เลือก” กับ “ล้างทั้งหมด”
4. **ประเมินสูตร**
   - ปุ่มกดได้เสมอ แต่ใช้ Toast บอกเงื่อนไขที่ยังขาด
   - ต้องตรวจ Project, สูตร, สาร, ข้อมูลสาร, สัดส่วน และรอยทาของสูตรที่เลือก
   - ส่งประเมินได้เมื่อสูตรที่เลือกมีรอยทาอย่างน้อยหนึ่งตำแหน่ง
5. **ดูผล**
   - ระหว่างรอ Backend แสดง progress ที่สื่อสถานะจริง
   - เมื่อผลสำเร็จ ครีมสีขาวค่อย ๆ จาง และอาการค่อย ๆ ปรากฏเฉพาะตำแหน่งที่ทา
   - แสดง Day 1/3/7, บริเวณที่ทา, อาการ, คะแนน, ระดับความเสี่ยง และความน่าเชื่อถือ
6. **กลับมาใช้งานต่อหลัง F5**
   - คืนสูตรที่เลือก รายการสาร รอยทา ผลล่าสุด วันที่เลือก และสถานะหน้าจอที่จำเป็น
   - ห้ามประเมินใหม่อัตโนมัติ และห้ามแสดงอาการของผลที่หมดอายุจากการแก้สูตร

### 15.3 การแก้ Logic ก่อนแตะ Layout

สิ่งที่โค้ดปัจจุบันยังไม่ตรงกับ Workflow ใหม่:

- `assessmentStartProblem()` ยังไม่รับสถานะรอยทา จึงยังไม่บังคับ “ทาก่อนประเมิน”
- `Viewport` ส่ง `armed={ready}` ให้โมเดล ทำให้ทาได้หลังมีผลประเมินเท่านั้น
- Workflow Chip ปัจจุบันมีเพียง “เตรียมสูตร → ประเมิน → ดูผลลัพธ์” และไม่มีขั้น “ทาโมเดล”
- ข้อความแนะนำบนโมเดลยังบอกให้ประเมินก่อน Paint
- ปุ่มยางลบบางสถานะยังผูกกับความพร้อมของผลประเมิน แทนที่จะผูกกับการมีรอยทา

ลำดับแก้ Logic:

1. เพิ่ม helper สำหรับตรวจความพร้อมของสูตรก่อน Paint แยกจาก helper ก่อน Assessment
2. เพิ่ม `hasPaint` ของสูตรที่เลือกเข้า assessment precondition
3. เปลี่ยนโมเดลให้ Paint ได้เมื่อสูตรผ่าน basic validation ไม่ใช่เมื่อ `completed`
4. ให้ผลอาการแสดงเฉพาะเมื่อ Assessment ของสูตรนั้นเสร็จและ signature ยังตรงกับสูตรปัจจุบัน
5. การเพิ่ม ลบ หรือเปลี่ยนเปอร์เซ็นต์สารต้อง invalidate ผลเดิม แต่เก็บพื้นที่ทาไว้เพื่อให้ผู้ใช้ประเมินสูตรฉบับแก้ไขในตำแหน่งเดิม
6. การลบสูตรต้องลบรอย ผล และ state เฉพาะสูตรนั้น
7. การเปลี่ยนสูตรต้องไม่ reload โมเดล ไม่ลบรอยของสูตรอื่น และไม่ย้ายกล้อง
8. ตรวจ persistence แยกตาม `projectId` และ `formulaId` หลัง F5

### 15.4 Information Architecture ใหม่บน Desktop

หน้า Desktop แบ่งเป็น 4 พื้นที่ตามลำดับงาน ไม่แบ่งตามโครงสร้างโค้ด:

1. **Top App Bar — บริบทและความคืบหน้า**
   - Logo/กลับโปรเจกต์
   - ชื่อโปรเจกต์ปัจจุบัน
   - Mode: ประเมิน / Nodes / ความน่าเชื่อถือ
   - Stepper: สูตร → สาร → ทาโมเดล → ประเมิน → ผลลัพธ์
   - PDF แสดงเมื่อมีผลพร้อมส่งออกเท่านั้น
2. **Experiment Navigator — เลือกการทดลอง**
   - รายการกล่องสูตร
   - ชื่อสูตร จำนวนสาร บริเวณทา และสถานะสั้น ๆ
   - สถานะที่ใช้: ยังไม่มีสาร / พร้อมทา / พร้อมประเมิน / กำลังวิเคราะห์ / มีผลแล้ว / สูตรถูกแก้ไข
   - สร้าง เปลี่ยนชื่อ และลบสูตรจากพื้นที่เดียวกัน
3. **Formula Workspace — เตรียมสูตร**
   - สารในสูตรและน้ำฐาน
   - เพิ่มจากคลัง, CSV และ OCR
   - แสดงผลรวม %, validation และคำเตือนในตำแหน่งใกล้ข้อมูลที่ผิด
   - พับเก็บได้เมื่อผู้ใช้กำลังทาหรืออ่านผล เพื่อเพิ่มพื้นที่โมเดล
4. **Model + Result Workspace — ทาและอ่านผล**
   - โมเดลเป็นพื้นที่หลักและไม่ remount เมื่อสลับสูตรหรือเปิด panel
   - Toolbar ใกล้โมเดลมีขนาดแปรง, ยางลบ, ล้างรอยที่เลือก และล้างทั้งหมด
   - Right Inspector เปลี่ยนเนื้อหาตาม state: คำแนะนำ → พร้อมประเมิน → กำลังวิเคราะห์ → ผลประเมิน

### 15.5 การนำทางผู้ใช้ครั้งแรกแบบ Progressive Guidance

ไม่ใช้ Tutorial Modal ขนาดใหญ่ แต่ใช้คำแนะนำตามบริบท:

- ไม่มีสูตร: เน้นปุ่ม “สร้างสูตรแรก” และซ่อนเครื่องมือที่ยังใช้ไม่ได้
- มีสูตรแต่ไม่มีสาร: Formula Workspace แสดง Empty state พร้อม CTA “เพิ่มสาร”
- มีสารแต่ยังไม่ทา: โมเดลแสดงคำสั้น “เลือกบริเวณบนโมเดลเพื่อทาสูตร” และเน้นเครื่องมือแปรง
- ทาแล้ว: แสดงสถานะ “พร้อมประเมิน” พร้อมสรุปสูตร พื้นที่ทา และปุ่มประเมิน
- กำลังประเมิน: ล็อกการส่งซ้ำเฉพาะสูตรนั้น แต่ยังสลับดูสูตรอื่นได้
- ประเมินเสร็จ: Toast “วิเคราะห์เสร็จสิ้น” และพา focus ไปสรุปผลโดยไม่หมุนหรือ reset กล้อง
- กดปุ่มในลำดับที่ยังไม่พร้อม: แสดง Toast ระบุสิ่งที่ขาดเพียงหนึ่งเรื่องที่ควรทำต่อทันที

### 15.6 State ของ Right Inspector

1. **No formula** — ยังไม่ได้เลือกสูตร
2. **Empty formula** — ยังไม่มีสารในสูตร
3. **Needs paint** — สูตรผ่าน validation แต่ยังไม่มีรอยทา
4. **Ready to assess** — แสดงชื่อสูตร จำนวนสาร สัดส่วนรวม และบริเวณที่ทา
5. **Assessing** — แสดงสถานะจาก Backend และป้องกันการส่งซ้ำ
6. **Completed** — แสดงผลตาม Day 1/3/7 พร้อมรายละเอียดบริเวณและอาการ
7. **Stale result** — สูตรถูกแก้หลังประเมิน; ซ่อนอาการเดิมและให้ประเมินใหม่
8. **Failed** — สาเหตุแบบอ่านง่ายและปุ่มลองใหม่

### 15.7 Visual Direction สำหรับงานวิจัย Skincare

- ใช้พื้นขาว/เทาอ่อนและ Teal ของโครงการเป็นสี action หลัก
- ใช้สีความเสี่ยงเฉพาะผลประเมิน ไม่ใช้ตกแต่งพื้นที่ทั่วไป
- Typography เน้นชื่อสูตร สาร เปอร์เซ็นต์ และคะแนนให้สแกนข้อมูลได้เร็ว
- ใช้ Lucide/SemanticIcon แทน Emoji ทั้งหมด
- ใช้คำศัพท์คงที่: “สูตร”, “สาร”, “บริเวณทา”, “ประเมิน”, “ผลประเมิน”
- แยกข้อมูล Input, Simulation และ Result ด้วยหัวข้อและ spacing ไม่ใช้กรอบซ้อนหลายชั้น
- ทุกคะแนนต้องมี label และระดับข้อความกำกับ ไม่พึ่งสีเพียงอย่างเดียว
- แสดง disclaimer ว่าเป็นการคัดกรองด้วยแบบจำลอง ไม่ใช่ผลทางคลินิก ในตำแหน่งที่อ่านได้แต่ไม่แย่งความเด่นจากผลหลัก

### 15.8 Motion ที่ต้องใช้

- เปิด/ปิด Formula Workspace: transform 250–300ms โดยโมเดลเลื่อนอย่างต่อเนื่อง ไม่กระโดด

##### 7. ลำดับลงมือทำและเกณฑ์รับงาน

1. สร้าง Data adapter รวม Curated/Registry/Local พร้อม deduplicate และ unit test กฎการชนกันของชื่อ/SMILES
2. ทำโครงหน้า, Sticky toolbar, Search/Category/Scope filter และ Virtualized list โดยยังไม่เปิดการแก้ข้อมูล
3. เชื่อมภาพ, ประเภท, สูตรโมเลกุล, น้ำหนัก และรายละเอียดสารเดิมแบบ lazy/cached
4. เชื่อม `เพิ่มลงสูตร` กับสูตรที่เลือก รวมสถานะไม่มีสูตร/มีสารซ้ำและ feedback หลังเพิ่ม
5. ทำ Local substance storage, Modal เพิ่ม/แก้/ลบ และกฎไม่เก็บซ้ำเมื่อมีสารในระบบ
6. ตรวจ Desktop ที่ความกว้าง Formula Panel หลายขนาด, จอแคบ, Keyboard, Registry offline, Storage error และรายการมากกว่า 1,000 รายการ

**ถือว่าเสร็จเมื่อ:** ผู้ใช้ค้นหา/กรองสารได้โดยไม่หน่วง, เห็นภาพ ชื่อ สูตรโมเลกุล และเปอร์เซ็นต์ชัดเจน, แยกประเภทด้วยเส้นคั่นได้, เปิดรายละเอียดเดิมได้, เพิ่มสารลงสูตรที่เลือกได้โดยไม่ซ้ำ, สารระบบไม่ถูกบันทึกเป็น Local และสาร Local แยกจากระบบชัดเจน

**สถานะรอบนี้:** ทำ Core UI และ Data flow แล้ว รวมการโหลด Registry, Search/Category, รายการแบบ windowed, รายละเอียดสาร และ Local storage พร้อมยุบ Header ให้ชื่อหน้าอยู่บรรทัดเดียวกับ Search และตัด Scope tabs, จำนวนผลลัพธ์, ป้ายสูตรปลายทาง, หัวคอลัมน์ และหัวกลุ่มคลังระบบที่ซ้ำกับชื่อหน้าออกตาม UI ล่าสุด จากนั้นลดความสูง/ขนาดข้อความของ Toolbar ให้สมส่วน ลบไอคอนหน้าชื่อหน้า และเพิ่ม semantic icon เฉพาะแต่ละประเภทใน Dropdown ตามคลังสารเดิม การใช้งานรายการสารเป็นคลิกซ้ายเพื่อเพิ่ม/นำออกจากสูตร คลิกขวาเพื่อดูรายละเอียด และแสดงเปอร์เซ็นต์แทนปุ่มเพิ่ม ล่าสุดเปลี่ยนตารางกลับเป็น Responsive ตามความกว้างพื้นที่จริง โดยรักษาการ์ดใกล้เคียง 270–300px และจำกัดความสูงชื่อ/การ์ดเพื่อป้องกันการซ้อนทับ เพิ่มเส้นคั่นรายประเภท เรียงเปอร์เซ็นต์ภายในประเภทจากมากไปน้อย และเพิ่มปุ่มดาวแบบแสดงเมื่อ Hover/Focus พร้อมเชื่อมรายการโปรดกับแถบ `เพิ่มสาร` ซึ่งเรียง `สารที่เพิ่มเอง` ไว้ก่อนรายการโปรดและหมวดระบบ อีกทั้งแจ้ง Toast เมื่อผู้ใช้คลิกการ์ดครั้งที่สองโดยยังไม่ได้เลือกสูตร พร้อมรวม UI `เพิ่มสารเปล่า` ของ Formula Panel และคลังสารให้ใช้ component เดียวกัน มี autocomplete/ภาพคำแนะนำและกฎตรวจชื่อ–SMILES ชุดเดียว โดยยังใช้ตารางแบบ windowed และโหลดภาพแบบ lazy เพื่อไม่ render ทั้งคลัง ผ่าน `type-check` และตรวจหน้า Desktop จริงแล้ว ส่วน production build ผ่านในรอบก่อนเปลี่ยนรูปแบบตารางล่าสุด งานที่ยังเปิดไว้ใน checklist คือ metadata สูตรโมเลกุลของ Local, recovery message สำหรับ Storage เสีย/เต็ม และ regression ชุดเต็ม

#### แผน A2 — Logic/Persistence หน้า `Nodes` หลัง UI

สถานะ: **L1–L3 ดำเนินการแล้วและปรับกติกา Graph Draft ตามการตรวจของผู้ใช้ — L4–L8 ยังไม่เริ่ม**

> Revision ล่าสุด — Graph ยังเป็น Draft และสร้างได้แม้ไม่เลือกสูตร แต่เมื่อเลือกหรือแก้กล่องสูตร ระบบต้อง Synchronize รายการสารจากกล่องสูตรเข้า Graph โดยรักษาตำแหน่ง/Edge ที่นำกลับมาใช้ได้ การเพิ่ม ลบ แก้ `%` หรือ Edge บน Graph จะยังไม่เขียนกลับรายการสารในกล่องสูตรจนกด `บันทึกเป็นสูตร`; ยกเว้น `บริเวณทดสอบ` ใน Result Node ที่ต้องเปลี่ยน Region ของกล่องสูตรที่เลือกทันทีและล้างผลประเมินเก่าของสูตรนั้น

##### ระบบเดิมก่อนเริ่มงาน Logic

- หน้า `Nodes` ไม่ได้เริ่มจากระบบว่าง: Project Workspace มี `graphByFormulaId` สำหรับเก็บ Snapshot แยกตาม Formula ID ใน LocalStorage อยู่แล้ว โดย Snapshot มี Node, Edge และ Viewport
- เมื่อเปิด Graph ระบบใช้สูตรที่เลือกใน Formula Panel เป็น `seed` แล้ว Synchronize สารในสูตรเข้ากับ Node ที่มีอยู่
- การเปลี่ยน Node ถูกส่งกลับไปบันทึก Snapshot แบบหน่วงสั้นประมาณ 150ms และมีการ Flush Snapshot ล่าสุดตอน Component ถูกถอดออก
- สารประเภท `สารในสูตร` และ `สารเสริมสูตร` ถูกแปลงเป็นรายการสูตรรูปแบบเดียวกันและส่งกลับ Formula Panel; ความแตกต่างปัจจุบันอยู่ที่บทบาทและ UI มากกว่ากติกาการคำนวณ
- Formula Panel รับสารเคมี **ทั้งหมดที่อยู่บน Canvas** แต่ Result Node เดินตาม Edge ย้อนกลับและประเมินเฉพาะสารที่มีเส้นทางเชื่อมถึง Result Node เท่านั้น
- การกด `บันทึกเป็นสูตร` ใช้สารและสารเสริมสูตรทั้งหมดที่มี SMILES และความเข้มข้นมากกว่า 0% โดยยังไม่ได้ผูกขอบเขตกับ Result Node ตัวใดอย่างชัดเจน
- เมื่อชื่อสาร, SMILES หรือความเข้มข้นเปลี่ยน ระบบล้างผลของ Result Node แต่การเปลี่ยน Edge หรือบริเวณทดสอบอาจยังเหลือผลเดิมที่ไม่ตรงกับ Input ล่าสุด
- แม้มีระบบบันทึกเดิมแล้ว แต่ยังไม่มี Regression ที่ยืนยันครบว่าข้อมูลไม่หายเมื่อสลับ Mode, สูตร, โปรเจกต์, รีเฟรช หรือปิด/เปิดหน้าใหม่ จึงยังห้ามสรุปว่าปัญหา Persistence แก้แล้ว

##### ปัญหา Logic ที่ต้องแก้

1. **ขอบเขตสูตรไม่ตรงกัน:** สูตรใน Formula Panel, สูตรที่บันทึกจาก Graph และสูตรที่ Result Node ส่งประเมินอาจเป็นคนละชุด
2. **ยังไม่ทราบจุดที่ข้อมูล Graph หาย:** ต้องวัดแยก Snapshot creation, debounce/flush, Mode switch, Formula switch, Project hydrate และการโหลด LocalStorage
3. **ผลประเมินเก่าอาจค้าง:** การเปลี่ยน Edge, บริเวณทดสอบ หรือชุดสารที่เชื่อมต่ออาจไม่ Invalidate ผลเดิมอย่างถูกต้อง
4. **Validation ยังไม่เป็นกติกากลาง:** สารซ้ำ, SMILES ว่าง/ผิด, ค่า 0%, ผลรวมเกิน 100% และการเติม Water/Base อาจถูกจัดการต่างกันระหว่าง Formula Panel, Graph และ Result Node
5. **ความหมายของคำสั่งบันทึกยังซ้ำกัน:** Auto-save Workspace และ `บันทึกเป็นสูตร` เป็นคนละงาน แต่พฤติกรรมยังต้องกำหนดให้ชัดว่าบันทึกสารชุดใดและสร้าง/เขียนทับสูตรอย่างไร
6. **Result Node หลายตัวยังไม่มีข้อกำหนด:** ต้องกำหนดว่าจะอนุญาตหลายผลต่อ Graph หรือจำกัดหนึ่งผลต่อสูตร และหากมีหลายตัวต้องแยก Input, Region, Job และผลลัพธ์ออกจากกัน

##### ลำดับการดำเนินงาน Logic

- [x] **L1 — ยืนยัน Source of Truth และกติกาของ Edge**
  - กำหนดให้ชัดว่า Formula Panel, Node บน Canvas หรือชุด Node ที่เชื่อมถึง Result เป็นเจ้าของสูตรจริง
  - แนวทางหลักที่ต้องการ: ชุดสารที่ส่งประเมินของ Result แต่ละตัวต้องมาจาก Node ที่มีเส้นทางเชื่อมถึง Result ตัวนั้นเท่านั้น; Node ที่ไม่เชื่อมถือว่าไม่ได้เลือกประเมิน
  - กำหนดบทบาท `สารในสูตร` กับ `สารเสริมสูตร` ว่าทั้งสองถูกส่ง QSAR เหมือนกันแต่เก็บ Role แยกไว้ หรือมีกติกาการคำนวณต่างกันจริง
  - กำหนดจำนวน Result Node ที่อนุญาตและขอบเขตของแต่ละ Result ก่อนแตะระบบบันทึกหรือ API

  ผลการดำเนินการ L1:
  - กำหนดให้สารประเภท `สารในสูตร` และ `สารเสริมสูตร` ทั้งหมดบน Canvas คงอยู่เป็น Graph Draft แต่เฉพาะสารที่เชื่อมถึง Result Node เท่านั้นที่เป็นสูตรสำหรับประเมินและ `บันทึกเป็นสูตร`
  - Result Node ยังรองรับหลายตัวเพื่อเลือก Region/Job และชุดสารแยกกันได้ โดยส่งเฉพาะสารที่มีเส้นทางเชื่อมถึง Result ตัวนั้นเข้า Assessment API
  - สารที่ไม่ได้เชื่อมจะคงอยู่ใน Graph Draft แต่ไม่ร่วมการประเมินและไม่บล็อก Result; หากไม่มีสารเชื่อมอยู่เลยจึงแจ้งให้ผู้ใช้เชื่อมสารก่อน
  - แยกฟังก์ชัน `formulaResultScope` สำหรับหา Connected/Disconnected chemical nodes แบบ Deterministic และป้องกันการเดิน Graph วนไม่สิ้นสุดเมื่อ Snapshot มี Cycle
  - เปลี่ยน `บันทึกเป็นสูตร` ให้ใช้ `formulaItemsConnectedToResults` ซึ่งรวมเฉพาะสารที่มีเส้นทางเชื่อมถึง Result Node อย่างน้อยหนึ่งตัว ส่วน Node ที่ไม่เชื่อมไม่ถูกบันทึก
  - โหมด Nodes ไม่เติม Water/Base ที่ไม่มี Node และเส้นเชื่อมโดยอัตโนมัติอีกต่อไป เพื่อให้จำนวนสารที่ส่งประเมินและบันทึกตรงกับ Graph ที่ผู้ใช้สร้าง
  - เพิ่ม Regression test ตามกรณีมีสาร 4 Node แต่เชื่อม Result เพียง 2 Node และยืนยันว่าชุดบันทึกมีเฉพาะ 2 สารที่เชื่อม; `formula-graph.test.ts` ผ่าน 15/15 รายการ
  - รอบ L1 ยังไม่รวมกฎ SMILES, สารซ้ำ, ค่า 0%, ผลรวมเกิน 100% และ Edge validation เชิงลึก ซึ่งเก็บไว้ทำใน L4 ตามขอบเขตเดิม
  - ตรวจด้วย `npm run type-check` และ Logic test `formula-graph.test.ts` ผ่าน 7/7 รายการ

- [x] **L2 — ตรวจและแก้ Persistence เดิมโดยไม่สร้างระบบซ้ำ**
  - ใส่จุดตรวจเฉพาะ Development เพื่อดูว่า Snapshot ถูกสร้าง ส่งไป Parent และเขียน LocalStorage ช่วงใด
  - ทดสอบแยกกรณี `ประเมิน ↔ Nodes`, สลับสูตร, สลับโปรเจกต์, รีเฟรช, ปิด/เปิดหน้าใหม่ และลบ Node ตัวสุดท้าย
  - ยืนยันว่า Key ถูกผูกกับ Project Workspace และ Formula ID ถูกต้อง ไม่มี Graph ข้ามสูตรหรือข้ามโปรเจกต์
  - ให้ Node, Edge, Viewport และข้อมูลภายใน Node ถูก Flush ก่อน Component ถูกถอดออก รวมถึงบันทึก Graph ว่างได้จริง

  ผลการดำเนินการ L2:
  - รักษาระบบเดิมที่เก็บ Workspace แยกด้วย Project ID และเก็บ Graph ภายในด้วย Formula ID โดยไม่สร้าง Storage หรือ Key ชุดใหม่
  - เพิ่ม Snapshot preview ที่ส่ง Node, Edge, Viewport และข้อมูล Node ล่าสุดไปเก็บใน Workspace draft ทันที ขณะที่การ Commit React state ยังคง Debounce 150ms เพื่อลด Render ระหว่างลาก Node
  - เมื่อสลับ Mode/สูตรหรือ Component ถูกถอดออก ยังคง Flush Snapshot ล่าสุดผ่านเส้นทางเดิม และ `pagehide` จะอ่าน Workspace draft ที่รวม Snapshot preview ล่าสุดแล้ว
  - แก้ `normalizeFormulaGraphSnapshot` ให้ยอมรับ Graph ที่มี `nodes: []` เป็นข้อมูลถูกต้อง ไม่ตีความเป็น Snapshot เสีย
  - แก้ `synchronizeGraphWithFormula` ไม่ให้สร้าง Result Node เริ่มต้นกลับมาเมื่อ Formula และ Snapshot ว่างโดยตั้งใจ ทำให้ลบ Node ตัวสุดท้ายแล้วรีเฟรชยังคง Empty State
  - ไม่ Mount FormulaGraph เมื่อยังไม่ได้เลือกสูตร เพื่อป้องกันการสร้าง Graph ที่ไม่มี Formula ID เจ้าของและไม่สามารถบันทึกแบบ Project-scoped ได้
  - เพิ่ม Regression test สำหรับ Project isolation, Formula ownership, Node/Edge/Viewport round-trip, Graph ว่าง และการไม่คืน Default Result หลังโหลด
  - ตรวจด้วย `npm run type-check` และ Logic tests `project-workspace.test.ts` + `formula-graph.test.ts` ผ่าน 22/22 รายการ; การตรวจสลับหน้า/รีเฟรชบน Desktop จริงรอผู้ใช้ตรวจรอบนี้

- [x] **L3 — ทำ Formula Panel ↔ Graph Synchronization ให้เสถียร**
  - เพิ่ม ลบ และแก้ `%` จาก Graph แล้ว Formula Panel ต้องเปลี่ยนครั้งเดียวโดยไม่สร้าง Feedback loop
  - การแก้ Formula Panel ต้องอัปเดต Node เดิมด้วย Stable identity โดยรักษาตำแหน่งและ Edge ไม่สร้าง Node ซ้ำ
  - กำหนดพฤติกรรมสารซ้ำให้เป็นกติกาเดียวกัน เช่น เลือกรายการเดิม, รวมรายการ หรือปฏิเสธพร้อม Feedback
  - การลบสูตรหรือลบสารต้องลบ Snapshot/Node ที่เกี่ยวข้องเท่านั้นและไม่กระทบสูตรอื่น

  ผลการดำเนินการ L3:
  - ปรับ Formula signature ให้ไม่ขึ้นกับลำดับรายการ จึงไม่ Sync วนหรือสร้างการเปลี่ยนแปลงปลอมเมื่อสูตรชุดเดิมเรียงคนละลำดับ
  - ใช้ SMILES ที่ Normalize แล้วเป็น Stable identity หลักและใช้ชื่อเป็น Fallback; หากผู้ใช้แก้ตัวตนสารจาก Formula Panel ระบบจะนำ Node ตำแหน่งเดิมกลับมาใช้แทนการลบและสร้างใหม่ จึงรักษาตำแหน่ง ประเภท Node และ Edge เดิมไว้
  - กำหนดกติกาหนึ่ง Chemical identity ต่อหนึ่ง Working Formula: เมื่อเลือกสารเดิมจาก Node picker ระบบโฟกัส Node เดิมและแสดง Toast แทนการเพิ่มซ้ำ
  - สำหรับข้อมูลเก่าหรือข้อมูลจากภายนอกที่มีสารซ้ำ ระบบรวมรายการด้วย Identity เดียวกันและรวมความเข้มข้น เพื่อไม่ให้ปริมาณสารหายระหว่าง Normalize
  - การเพิ่ม ลบ หรือแก้ `%` ใน Graph ยังคงส่ง Formula change เพียงเมื่อ Signature เปลี่ยนจริง ขณะที่การลาก Node หรือแก้ Edge ไม่เขียนทับรายการสารใน Formula Panel
  - เพิ่มการลบ Graph Snapshot ที่ไม่มี Formula เจ้าของและปฏิเสธ Late snapshot callback หลังสูตรถูกลบ ป้องกัน Snapshot ของสูตรที่ลบแล้วกลับเข้ามาใน State
  - ปรับตาม Revision ล่าสุดให้สูตรที่เลือก Synchronize รายการสารเข้า Graph ทั้งตอนเปิดและเมื่อกล่องสูตรเปลี่ยน โดย Graph ที่ไม่มีสูตรยังคงเป็น Project Draft อิสระ
  - เชื่อม Region ของ Result Node กลับไปยังสูตรที่เลือกทันที; การสลับ `ใบหน้า/ดวงตา` จะอัปเดตไอคอน/ข้อมูลกล่องสูตรและ Invalidate ผลประเมินเดิม ส่วนการแก้สารบน Graph ยังไม่เขียนกลับจนกด `บันทึกเป็นสูตร`
  - รอบ L3 ยังไม่ตัดสินความถูกต้องของผลรวมหลังรวมสารซ้ำหรือ SMILES เชิงโครงสร้าง ซึ่งทำต่อใน L4
  - ตรวจด้วย `npm run type-check` และ Logic tests `project-workspace.test.ts` + `formula-graph.test.ts` ผ่าน 29/29 รายการ

- [ ] **L4 — รวม Validation ของสูตรไว้ชุดเดียว**
  - ตรวจชื่อสารและ SMILES ก่อนอนุญาตให้ประเมินหรือบันทึกเป็นสูตร
  - จำกัดความเข้มข้นแต่ละสารเป็น 0–100% และปฏิเสธผลรวมที่เกิน 100% ด้วยข้อความที่ชัดเจน
  - ใช้กฎ Water/Base เติมส่วนที่เหลือให้ครบ 100% ชุดเดียวกับ Assessment ปกติ
  - ตัดสินให้ชัดว่าสาร 0% จะถูกเก็บเป็น Draft หรือไม่ส่งเข้า Formula/Assessment และใช้กติกานี้ทุกจุด
  - ป้องกัน Self-loop, Edge ซ้ำ, Cycle ที่ผิดกติกา และ Result ที่ไม่มี Input ที่ประเมินได้

- [ ] **L5 — จัดการ Lifecycle ของ Result Node**
  - สร้าง Input signature จากสาร ความเข้มข้น Edge และ Region ที่ Result ตัวนั้นใช้จริง
  - เมื่อ Input เปลี่ยน ให้ล้างผลเก่าและแสดงสถานะ `ยังไม่ประเมิน` ทันที ไม่ปล่อยคะแนนเก่าค้าง
  - ป้องกันการส่ง Job ซ้ำขณะ `queued/running` และผูกผลตอบกลับกับ Result Node ที่เริ่ม Job เท่านั้น
  - ยกเลิก Polling เมื่อ Result ถูกลบ, เปลี่ยนสูตร, เปลี่ยนโปรเจกต์ หรือออกจากหน้า และป้องกัน Response เก่ากลับมาเขียนทับ State ใหม่
  - กำหนดการกู้สถานะ Job หลังรีเฟรชว่าจะ Resume จาก Job ID หรือกลับเป็นยังไม่ประเมินอย่างปลอดภัย

- [ ] **L6 — แยก Auto-save Graph ออกจาก `บันทึกเป็นสูตร`**
  - Auto-save ต้องคง Graph เดิมไว้ต่อโปรเจกต์/สูตรโดยไม่ต้องกดปุ่ม
  - `บันทึกเป็นสูตร` ต้องสร้างสูตรใหม่จากชุด Node ตามกติกา L1 พร้อม Stable ID และไม่เขียนทับสูตรต้นทางโดยไม่แจ้ง
  - ตรวจสารซ้ำ, ผลรวม, Water/Base และ Node ที่ไม่สมบูรณ์ก่อนสร้างสูตรใหม่
  - หลังสร้างสำเร็จต้องเลือก/ไม่เลือกสูตรใหม่ตามกติกาที่กำหนดไว้ชัดเจนและไม่ทำ Graph ต้นทางหาย

- [ ] **L7 — รองรับ Snapshot เก่าและความเสียหายของ Storage**
  - Normalize Snapshot รุ่นเก่าและบริเวณเดิมที่ไม่ใช่ `face/eye` โดยไม่ทำให้หน้า Error
  - หาก Node บางตัวเสีย ให้เก็บส่วนที่อ่านได้และแจ้ง Recovery แทนการลบ Graph ทั้งชุด
  - จัดการ LocalStorage เต็ม, JSON เสีย และ Version migration โดยไม่เขียนทับข้อมูลเดิมก่อนกู้คืน

- [ ] **L8 — เพิ่ม Tests และ Regression ก่อนถือว่า Logic เสร็จ**
  - Unit test: Graph ↔ Formula mapping, Input signature, Edge traversal, Duplicate, Concentration total, Water/Base และ Snapshot migration
  - Integration test: สลับ Mode/สูตร/โปรเจกต์, รีเฟรช, Graph ว่าง, แก้ %, ลบ Node, เปลี่ยน Edge/Region และ Result หลายตัวตามกติกา L1
  - ทดสอบกับ API stub ก่อน แล้วแยกรายงานให้ชัดว่าผ่านเฉพาะ Frontend integration หรือผ่าน Backend/QSAR จริง
  - รัน `npm run type-check`, Logic tests, `npm run build` และตรวจหน้า `/assess` จริงก่อนปิดงาน

##### เกณฑ์ที่ถือว่า Logic/Persistence เสร็จ

- สูตรที่แสดงใน Formula Panel, สูตรที่บันทึก และ Input ที่ Result ส่งประเมินตรงกันตามกติกาเดียวกัน
- Node, Edge, Viewport และข้อมูล Result ไม่หายหรือข้ามสูตร/โปรเจกต์หลังการสลับหน้าและรีเฟรช

- Formula และ Graph Synchronize กันโดยไม่เกิด Node ซ้ำ, Edge หาย หรือ Update loop

#### แผน A2 — Model Toolbar สำหรับการทาและลบ

สถานะ: **ดำเนินการแล้ว**

- ไม่เพิ่มปุ่ม `แปรงทา` เพราะการเลือกกล่องสูตรเป็นตัวกำหนดเจ้าของรอยทาโดยตรง เมื่อมีสูตร active โมเดลจะอยู่ในโหมดทาของสูตรนั้นโดยอัตโนมัติ
- เมื่อไม่มีสูตร active ต้องปิดการทาบนโมเดล ปิดคำสั่งลบ และปิดปุ่มประเมิน พร้อมบอกให้ผู้ใช้เลือกกล่องสูตรก่อน
- การ์ดสถานะซ้ายบนต้องแสดงบริบทของสูตรที่กำลังทา เพื่อให้ยังทราบเจ้าของรอยทาแม้ Formula Panel ถูกย่อ
- ย้ายบริบท `กำลังทา: [ชื่อสูตร]` ไปอยู่การ์ดสถานะซ้ายบนแทนคำว่า `ทาบนโมเดล` และนำบริบทที่ซ้ำออกจาก Toolbar ด้านล่าง รวมถึงซ่อนการ์ด `พร้อมประเมินสูตร` เมื่อมีรอยทาพร้อมแล้ว
- ย่อ Model Toolbar ให้กระชับและไม่มีเงา เปลี่ยนชื่อ `ยางลบ` เป็น `ลบรอย` และแสดงคำสั่งประเมินเป็นไอคอนพร้อมข้อความ `เริ่มประเมิน`
- นำการ์ดสถานะด้านขวาบนของพื้นที่โมเดลออกทั้งหมด เพื่อลดข้อความเตรียมสูตร/พร้อมทา/กำลังวิเคราะห์ที่ซ้ำกับส่วนควบคุมอื่น
- ย่อการ์ดสถานะซ้ายบนให้เหลือบรรทัดเดียว `ยังไม่ได้เลือกสูตร` หรือ `เลือกสูตร [ชื่อสูตร] อยู่` และใช้ไอคอนสูตร/บริเวณแทนหมายเลขขั้นตอน
- คง `ยางลบ` เป็น toggle สำหรับระบายลบบางส่วน และเพิ่ม `ลบทั้งหมด` สำหรับลบ mask เฉพาะสูตร active โดยไม่แตะรอยของสูตรอื่น
- `ลบทั้งหมด` ต้อง disabled เมื่อสูตร active ยังไม่มีรอยทา และต้องมีการยืนยันพร้อมระบุชื่อสูตรก่อนลบ
- ไม่เพิ่มปุ่มขนาดแปรง S/M/L บน Toolbar ให้ใช้ `Ctrl + ลูกกลิ้งขึ้น/ลง` เหนือพื้นที่โมเดลเพื่อปรับขนาดหัวทาและยางลบแบบต่อเนื่องแทน
- ระหว่างกด `Ctrl + ลูกกลิ้ง` ต้องหยุดการซูมกล้องชั่วคราว และจำกัดขนาดหัวทาให้อยู่ในช่วงที่ใช้งานได้
- ไม่แสดงวงขนาดหัวทา เหลือเพียงข้อความ `หัวทา xx%` หลังปรับขนาด โดยข้อความติดตามเมาส์ช่วงสั้น ๆ แล้วค่อย ๆ จางหาย
- ปรับค่าขนาดหัวทาที่ผู้ใช้เห็นเป็นช่วง 10–100% เพิ่ม/ลดครั้งละ 1% โดย map ค่า 10 ไปยังขนาด renderer 20 และค่า 100 ไปยังขนาด renderer 85 แบบเส้นตรง
- เพิ่ม wheel acceleration สำหรับขนาดหัวทา: เลื่อนช้าปรับละเอียดขั้นต่ำ 1% ส่วนการเลื่อนแรงหรือเร็วปรับได้สูงสุด 10% ต่อ event โดย normalize ทั้ง mouse wheel และ trackpad เพื่อลดจำนวนรอบจาก 10 ไป 100
- เพิ่มปุ่มประเมินเป็นความสูง 36px และความกว้างขั้นต่ำ 112px พร้อมข้อความ `เริ่มประเมิน` เพื่อให้ Primary action ชัดเจนขึ้น
- การเลื่อนลูกกลิ้งตามปกติโดยไม่กด `Ctrl` ยังคงใช้ซูมโมเดลเหมือนเดิม และนำป้ายคำแนะนำด้านบนโมเดลออกตามรูปแบบ UI ล่าสุด
- ปุ่ม `ประเมินสูตร` ยังคงเป็น Primary action แยกจากกลุ่มคำสั่งลบรอยด้วย divider และใช้กติกาเดิมว่าต้องเลือกสูตร สูตรพร้อม และมีรอยทาก่อน
- ปรับ Tooltip ของรอยทาให้ระบุตำแหน่งจากพิกัดดวงตา ขอบเขตผิวทั้งหมด และความลึกของโมเดล เพื่อให้ตำแหน่งไม่เปลี่ยนผิดเมื่อหมุนกล้อง พร้อมเพิ่ม `หูซ้าย/ขวา`, `หลังใบหูซ้าย/ขวา`, `หลังศีรษะ`, `หลัง` และ `ลำตัว`
- ปรับ Tooltip ผลบนโมเดลเป็นการ์ดขนาดกะทัดรัด โดยแสดงชื่อบริเวณแบบสั้นต่อท้ายชื่อสูตรในบรรทัดเดียวโดยไม่มีคำว่า `ตำแหน่ง` ตามด้วยสถานะตามช่วงเวลาและรายการคะแนน `/100` บนพื้นหลังแยกส่วน เพื่อลดข้อความที่บังโมเดล
- ปรับ collision ของรอยทาระหว่างสูตรจากการยกเลิกหัวทาทั้งวงเมื่อขอบชน เป็นการตัดเฉพาะพิกเซลที่สูตรอื่นครอบอยู่ ทำให้รอยของสองสูตรเข้าใกล้กันได้ตามขอบจริงโดยยังไม่ซ้อนทับ และแจ้งเตือนเฉพาะเมื่อพื้นที่ใช้งานของหัวทาถูกครอบทั้งหมด
- ปรับ `ลบทั้งหมด` ให้ล้างการแสดงผลบนโมเดลของสูตร active ครบทั้ง paint mask บนผิว ระคายเคืองตา และผลเชิงระบบที่ไม่อยู่ใน mask โดยยังเก็บสูตรและข้อมูลผลประเมินไว้ และไม่แตะรอยของสูตรอื่น
- แก้ orphan paint หลังลบสูตรขณะไม่มีสูตร active: renderer ต้องสร้าง occupied mask ใหม่เมื่อจำนวน snapshot ของสูตรอื่นเปลี่ยน รวมถึงกรณีเหลือศูนย์ และ workspace ต้องคัดทิ้ง paint snapshot ทุก id ที่ไม่มีกล่องสูตรเจ้าของแล้ว เพื่อไม่ให้รอยค้างโดยไม่มีปุ่มลบ

6. Shader ผิว โมเดล animated eyes และ DPR สูงสุด 1.5 เป็นภาระ GPU พื้นฐาน แต่ปริมาณพื้นที่ที่ทาไม่ได้เพิ่มจำนวน geometry จึงไม่ใช่สาเหตุหลักของการช้าลงตามจำนวนรอย

ลำดับดำเนินการ:

- [x] **O1 — ตัดงานซ้ำใน hot path (ดำเนินการแล้ว):** เพิ่ม fast path เมื่อไม่มีรอยจริงจากสูตรอื่น โดยข้าม collision read/temporary mask ทั้งหมด ไม่โหลด snapshot ว่างมาเป็น occupied mask และตรวจ blocked state เฉพาะตอนจำเป็นแทนการ `getImageData()` ทุก dab
- [ ] **O2 — จำกัดงานต่อเฟรม (rollback แล้ว ต้องออกแบบใหม่):** การ queue เฉพาะ UV ล่าสุดต่อ animation frame ทำให้จุด `pointermove` กลางทางหายและเกิดเส้น interpolation ข้าม UV จากรอบตาไปจมูกหรือปาก จึงคืนการวาดทุก `pointermove` และเพดาน 32 dab ให้ตรงกับ `main`; หากทำใหม่ต้องเก็บ path ย่อยครบ ไม่ใช่ latest-only
- [x] **O3 — Batch texture update (ดำเนินการแล้ว):** วาด dab ทั้งหมดของเฟรมก่อนแล้วตั้ง `needsUpdate` เพียงครั้งเดียวต่อ texture รวมทั้ง occupied texture ปิด mipmap สำหรับ canvas mask และใช้ linear filtering ที่เหมาะกับ mask 2D
- [x] **O4 — ใช้ exposure mask เดียวใน Assessment (ดำเนินการแล้ว):** ให้ endpoint ทั้ง 4 อ่าน CanvasTexture พื้นที่ทาร่วมกันเพียงชุดเดียว บันทึก snapshot ใหม่ด้วยคีย์ `exposure` เก็บ mask แยกเฉพาะหน้า standalone Symptom Lab และรวม snapshot 4 ชั้นเก่าเป็น mask เดียวก่อนบันทึกกลับโดยไม่เพิ่ม workspace version
- **O5 — ย้าย snapshot ออกจาก main interaction:** เปลี่ยนการเข้ารหัส exposure mask เดียวจาก O4 เป็น `toBlob()`/`OffscreenCanvas.convertToBlob()` แบบ asynchronous และไม่ให้การปล่อยเมาส์รอการบีบอัดภาพ
- **O6 — แยก persistence:** เก็บ paint blob ใน IndexedDB และให้ localStorage เก็บเฉพาะ metadata/สูตร หรืออย่างน้อยเลื่อนการ serialize ไปช่วง idle พร้อม debounce ที่ยาวขึ้น โดยยัง flush อย่างปลอดภัยตอนออกจากหน้า
- **O7 — ปรับ GPU เมื่อยังจำเป็น:** ลด DPR ชั่วคราวเฉพาะระหว่างลากและพัก animation/hover effect ที่ไม่จำเป็น แล้วคืนคุณภาพหลังหยุดทา โดยทำหลัง O1–O6 เพื่อไม่ลดคุณภาพก่อนแก้ต้นเหตุ

เกณฑ์ยอมรับก่อนถือว่า Optimize เสร็จ:

- ระหว่างลากไม่มี main-thread long task เกิน 50ms และ paint work ต่อเฟรมเป้าหมายไม่เกิน 8ms บนเครื่องทดสอบหลัก
- การปล่อยเมาส์ต้องตอบสนองต่อ UI ภายใน 50ms แม้มีรอยกว้างและหลายสูตร ส่วนการบันทึกทำต่อเบื้องหลังได้
- รักษาเฟรมเรตเป้าหมายอย่างน้อย 50 FPS ระหว่างลากบน viewport desktop มาตรฐาน
- รอยของสูตรต่างกันยังเข้าใกล้กันได้โดยไม่ซ้อนทับ การลบ/Undo persistence และการโหลด workspace เก่ายังทำงานครบ
- ยังไม่เพิ่ม Reset camera, ซ่อน/แสดงผล, Undo/Redo หรือคำสั่งจัดพื้นที่โมเดลในรอบ Toolbar นี้ เพราะจะพิจารณาร่วมกับงานหัวข้อถัดไปเรื่องการแสดงผลและการจัดการพื้นที่ตรงกลาง

#### ประเด็นรอพิจารณา — พฤติกรรมเมื่อเลือกบริเวณดวงตา

สถานะ: **บันทึกไว้เพื่อพิจารณา ยังไม่อนุมัติให้แก้ไขหรือเพิ่ม Scope ใน A2**

- ปัจจุบันตัวเลือก `ดวงตา` ใช้ Workflow, โมเดลศีรษะ, เครื่องมือทา และหน้าผลลัพธ์แบบเดียวกับ `ใบหน้า` โดยยังแสดงผลครบ 4 endpoints
- Backend นำ region ไปปรับคะแนนจริง: `face` ใช้ตัวคูณ skin ×1.3 / eye ×0.5 ส่วน `eye` ใช้ skin ×1.1 / eye ×1.6 ขณะที่ sens และ acute ไม่เปลี่ยน
- คะแนน eye ควบคุมภาพตาขาวแดงทั้งสองข้าง แต่การเลือก `ดวงตา` ยังไม่ซูมเข้าตา ไม่จำกัดพื้นที่ทาเฉพาะรอบดวงตา และไม่มี validation หรือคำเตือนเฉพาะผลิตภัณฑ์รอบดวงตา
- ข้อจำกัดทางวิทยาศาสตร์ที่ต้องพิจารณาก่อนขยาย UI: ข้อมูลฝึก eye ปัจจุบันยังซ้ำกับ skin จึงยังไม่ใช่ eye model ที่ยืนยันด้วยชุดข้อมูลอิสระ
- หากตัดสินใจปรับในภายหลัง ให้พิจารณาแยกเป็น 3 ส่วน: (1) Eye-focused UI/การซูมและพื้นที่ทา (2) การจัดลำดับผลและคำเตือนเฉพาะดวงตา (3) การปรับ dataset/model และทบทวน region sensitivity
- ก่อนเริ่มแก้ ต้องตัดสินใจก่อนว่าจะคงชื่อ `ดวงตา` หรือเปลี่ยนเป็น `รอบดวงตา` และต้องการให้เป็นเพียงการเน้นผล eye หรือเป็น Workflow เฉพาะที่จำกัดการทาและการประเมินจริง

> Decision gate: ห้ามเริ่ม implementation ของ Eye-specific Workflow จนกว่าผู้ใช้จะยืนยัน Scope และแนวทางที่ต้องการ

> หมายเหตุ: UI ใน A2 เป็นการปรับตามคำสั่งและภาพอ้างอิงที่ผู้ใช้ระบุ การเปลี่ยนส่วนถัดไปต้องรอให้ผู้ใช้กำหนดตำแหน่งและรูปแบบก่อนดำเนินการ
